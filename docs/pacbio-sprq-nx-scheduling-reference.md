# PacBio SPRQ-Nx / Revio scheduling reference

Distilled from PacBio's *Technical overview: Revio system v13.5 + SPRQ-Nx chemistry and SMRT Link v26.1* (PN 103-849-300 Rev 01, May 2026 — PacBio confidential vendor material; the PDF itself is not checked into this repo). This file captures the engineering-relevant facts only, mapped onto this app's actual entities, for whoever next touches cell-reuse or scheduling logic.

Page numbers below refer to that source deck.

## Hard constraints from the instrument — already modeled correctly

1. **Max 3 uses per multi-use SMRT Cell.** PacBio: "Each multi-use SMRT Cell supports up to 3 acquisitions (uses)" (p.10, p.25). App: `Cell.max_uses` defaults to 3, capped `Literal[1, 2, 3]` (`schemas/run.py:58,71`); consumption is always derived live from non-cancelled `CellUse` rows in `derive_cell_state()` (`services/cell_service.py:44-55`), never re-entered by hand — this mirrors the instrument's own auto-tracking rather than trusting operator bookkeeping.

2. **The 108-hour window is one absolute deadline from Use 1, not a per-use timer.** PacBio: "Once removed from cell tray for 1st use, the 3rd use (Use 3) must start within 108 hours (= 4.5 days)"; the countdown "starts when SMRT Cell is first removed from the cell tray for 1st use" (p.25, p.28) — it does **not** reset at Use 2. App: `CELL_LIFETIME_H = 108` (`engine/constants.py:8`), checked as elapsed hours from `Cell.first_use_started_at` in `recompute_status()` (`services/cell_service.py:30-33`). This is the right semantics — resist any "fix" that turns it into a per-use reset.

3. **Expired or exhausted cells are terminal — the instrument allows no override.** PacBio: "NO option to use expired multi-use SMRT Cells for a sequencing run" (p.25, pp.28-30) — enforced by the instrument itself, not a soft warning. App: `remaining <= 0` → `status = "exhausted"`; `window_breached` → `status = "window_expired"` (`services/cell_service.py:36-39`); `place_sample()` raises 409 when a cell has no remaining uses (`services/placement_service.py:125-128`). **Asymmetry to note:** placement does *not* currently 409 on `window_breached` the same way it does on exhaustion — window state today only surfaces as a scheduling-time warning (`window_flags`). See Gaps below.

4. **A cell, once broken out of its tray, never goes back — reuse is strictly sequential.** PacBio: "Once removed from tray, a SMRT Cell is never returned to the tray" (p.25). Starting Use 1 commits a cell to the 108h clock with no undo. App's requirement that a cell's next use fall on a strictly later date (no same-day or out-of-order reuse) is consistent with this — don't add a path that lets a scheduled use be reordered ahead of an earlier one on the same cell.

5. **Reuse is always prioritized over opening a new cell.** PacBio: the instrument "automatically tracks SMRT Cell uses and prioritizes allocation of samples to used cells before new cells" (p.24), explicitly so operators skip loading a second tray when reuse capacity already covers the remaining samples ("There is no need to load SMRT Cell tray 2," p.24). App: both `pack_cells()` and `fill_slots()` sort candidates `(0 if prior else 1, -len(uses))` (`engine/packing.py:69`, `engine/slot_scheduling.py:25`) — reusable cells always sort before fresh ones, most-used first. Already correct; also a good source of user-facing copy if the UI ever wants to explain *why* it picked particular cells ("N reuse slots available — no new cells needed").

## Plate vs cell: the weekly grid tracks loading positions, not cells (v0.12.0)

**Display re-tightened 2026-08-07 (see "Sequential wells take sequential cells" below):** the *physical* independence described here still holds (cell trays and sample plates are separate positions; a cell is pinned to its tray position for life; cross-box reuse is allowed), but the *displayed* well→cell-number mapping within a plate is no longer free to diverge arbitrarily — it is re-sequenced ascending on every drop, so a plate always reads cells 1,2,3,4 in well order. Read this section for the physical model, then that entry for the current display rule.

**This section supersedes the earlier "a physical cell is fixed to its own well for life; you must drop a sample onto that exact well" invariant.** Reported by the lab owner: after a cell was used its full 3 times (reused across Mon/Tue/Wed in one well) the grid rendered that well as a non-droppable ✕ "spent well" and blocked all further loading there — but on a Revio you can load one plate every weekday; the instrument just reaches for additional cells. The fix was to stop conflating two different things the grid was overloading onto one "well":

**Physical model: cell trays and sample plates are independent.** The instrument holds cell trays (4 SMRT cells each) and sample plates in **separate** positions; up to two of each. A sample plate is backed by cells from **either** cell tray, and a cell tray can supply **either** sample plate — operators just fill the first open cell-tray slot and the first open sample-plate slot. A **single plate load** draws all its cells from **one** cell tray (never a mix — the cohesion guard, see commit 94571ae), but **which** tray is not tied to the plate's position (Plate 1 may run on tray 2's cells). A cell is pinned to its **instrument + cell tray + tray position (1–4)** for life — **not** to a plate box; `Cell.home_well`'s `01`/`02` suffix only records where it was first loaded and must never gate which sample plate can later reuse it. **The code now honours this** (Stage 1 v0.40.1 auto-fill, Stage 2 v0.40.2 manual + fresh-tray allocation — see resolved "Gaps" #7).

- A **plate slot** (a grid well) is a **loading position** — where the operator drops a sample. It *never* "exhausts"; only a **cell** does. A plate slot is always droppable (unless the instrument is locked, or a stopped cell physically holds that exact well as a QC marker).
- A **physical cell** is auto-allocated by the instrument (the ICS "reuse before new; use the cell expiring next / next in order" behaviour). Cell identity/state surfaces **only** via the card's ticket-stub and the tray-disposal/expiry warnings — never by blocking a grid slot.

**Data model:** `CellUse.well` is now the **plate loading position** the sample was dropped onto (`WELLS[slot_index]`), which drives the grid slot (`run_serializer._slot_index`). `Cell.home_well`/`tray_position` remain the cell's **identity** (its fixed A/B/C/D tray position) and drive the stub letter (`StageOut.cell_home_well`) — so a sample loaded in slot A01 but running on cell B reads "B1". The two can now differ; before this change every row happened to have `well == home_well`, which stays a valid special case (no migration needed).

**A cell is pinned to its instrument + cell tray + tray position (1–4), not to a plate box.** A cell may be reused under **either** sample plate on its instrument (subject to the one-tray-per-plate cohesion guard, the 3-use cap, the single 108h window, one use per calendar day, and barcode-disjointness). `current_location()` returns the cell's `home_well`, whose **letter** (tray position) is the real pin; the `01`/`02` suffix is where it was first loaded, **not** a constraint on which plate can reuse it. The other guards are unchanged: instrument pin, capacity (3-use cap), the single 108h window, barcode-disjointness, and no out-of-order insert of a use ahead of an already-started later one. Both the auto-fill engine (`fill_slots`) and the manual path (`derive_best_cell`) now reuse across boxes by tray position; a fresh tray loads into a free carousel bay (`open_new_tray`). See resolved "Gaps" #7.

**Cell selection** (`placement_service.derive_best_cell` / `_pick_next_reuse_cell`; `stop_cell`'s reshuffle): reuse-before-new, **most-used cell first** (≈ "expiring next", since the most-used cell's 108h clock is nearest its deadline), then earliest first-use, then tray position — the same ordering `pack_cells`/`fill_slots` already use. A drop onto a slot resolves to the next-usable cell in that carousel position; the card stays in the dropped slot; only its stub names the real cell. Manual drag-and-drop (place *and* move) and Auto Schedule all flow through this.

**Stopping a cell reshuffles the tray** (`cell_service.stop_cell`): its not-yet-run *later* uses (chronologically after the trigger) are re-homed onto the tray's remaining cells — each keeps its day and plate slot; only which cell backs it changes. Whatever no longer fits (the stopped cell's lost capacity shortened the queue) can't run: those samples go back to the backlog (ABORTED_PRIORITY) and are reported as `unrunnable_sample_ids` so the user is alerted (`CellStopOut`). The triggering use is still treated as a Fail (its sample lost, drives the credit workflow); uses *before* the trigger are untouched. `undo_stop_cell` reverses all three kinds (failed / reassigned / cancelled-overflow), with a drift guard per use.

**The historical "must stay in its own well" bug-fix notes below (in "Tray-of-4 eager population" and the bug-history paragraphs) describe the *superseded* model** — they're kept for provenance of how the code evolved, but the well-pin guards, `wellConflict` machinery, and the spent-well ✕ they describe were removed in v0.12.0. The instrument-pin invariant ("a cell can never move between instruments") is unaffected and still holds.

**Refinement (reported by the lab owner, 2026-07-26): a *fresh* cell must always be the earliest cell in tray order — while cell A still has capacity, slot A01 shows *cell A*, never "cell B, Use 1".** The lab owner reported a Plate-1 grid where loading slot A01 showed **cell B, Use 1** while cell A of the same tray was itself only on Use 1 (i.e. still had capacity). On a fresh cell the instrument always breaks out the earliest cell in the tray (tray position A → B → C → D); a first use never lands on cell B while cell A is unused / has capacity. Slot A01 may legitimately draw **cell B Use 1 only once cell A is fully used** (all 3 uses spent) — this is the same "earliest cell with capacity" rule already applied to reuse (rule #5; "most-used-first" ≈ "earliest-with-capacity" within a normally-ordered tray, since the two only diverge in an already-broken, out-of-order tray).

- **Pure placement already obeys this.** `open_new_tray(well)[0]` returns the sibling whose `home_well == well`, and `_pick_next_reuse_cell`'s `(-consumed, started, tray_position)` sort tie-breaks all-fresh siblings by tray position (A first). So a fresh drop onto the earliest free loading slot always lands on the earliest cell, and only draws a later-lettered cell once the earlier one is spent (the *legitimate* well ≠ home divergence — e.g. an exhausted cell A leaves slot A01 showing cell B). No sequence of *placements* can put cell B in slot A01 while cell A still has capacity.
- **A *move* is what breaks it.** Commit `1bf8b7e`'s v0.12.0 contract makes a drag to a different slot in the *same* carousel box keep the sample's physical cell and merely rewrite `CellUse.well` to the destination slot (`move_sample`'s in-place reschedule; the only reassignment trigger left is the *box*-level `_cell_box` check — the earlier well-level `home_well != dest_well` guard was removed here, together with `_resolve_cell_choice`'s "must stay in its own well" check and `_existing_cell_well`). This is what `test_move_to_a_different_slot_in_the_same_carousel_position_keeps_the_cell` asserts. So dragging cell A's use from slot A01 to slot B01 leaves cell A (home A01) rendered in slot B01; a later fresh drop into the now-empty A01 resolves (reuse-before-new) to the next tray-order sibling, cell B — producing exactly the reported "slot A01 = cell B Use 1 while cell A still has capacity" transposition (both cells at Use 1, each sitting in the other's home slot). It is an easily-hit path: reorder two cards within one day. **Fixed (v0.14.4, 2026-07-26):** `move_sample` now treats *any* move to a different loading well (`dest_well != cell_use.well`) as a reassignment - the sample is handed to the cell the instrument reaches for at the destination slot via `derive_best_cell`, which is passed a new `exclude_cell_id` so the moved cell can't re-adopt itself into a foreign well (a reused / most-used cell would otherwise be re-picked and simply stored at the new well, reintroducing the divergence). A *same-well* move (same slot, another day) still keeps the cell in place - it's a plain reschedule. So only pure placement can now surface a later cell in slot A01, and only once cell A is genuinely spent - exactly the lab owner's rule. Covered by `test_move_endpoint.py::test_move_to_a_different_slot_in_the_same_carousel_position_reassigns_the_cell`, `test_move_to_a_different_well_in_the_same_position_reassigns_to_the_sibling_there`, and the regression `test_move_within_a_box_cannot_strand_a_fresh_cell_out_of_slot_a01`.

## Tray-of-4 eager population

SMRT Cells physically ship in a tray of 4. The moment any one cell in a tray gets a sample, all 4 are registered as real `Cell` rows together (`services/cell_service.py::open_new_tray()`), not lazily — 3 are left `status="open"`, 0 uses, ready to be picked up later. This is called from both "open a new cell" sites: `placement_service.place_sample()` (mode `"new"`) and `auto_fill_service.auto_fill()`'s persist loop.

- **A tray of 4 is one physical object — disposal is ALL-OR-NOTHING across the whole tray, never per cell.** The 4 cells share one physical tray that loads into, and is physically removed from, a single **cell-tray** slot as one unit; each cell keeps its **tray position (1–4)** for life (`Cell.home_well`'s letter). (The tray's slot is a cell-tray position, *not* a sample-plate/well box — a plate can draw from either tray; see "Physical model" under "Plate vs cell".) So **you cannot throw away one cell and keep its siblings** — physically binning the tray discards all 4 at once, regardless of how much capacity any of them has left. This is distinct from *natural attrition*: an individual cell going `exhausted` (hit its 3-use cap) or `window_expired` while a sibling is still `open` is fine — the spent cell is simply sitting inert in a tray that physically remains on the instrument because a sibling still has capacity. The tray only truly *leaves* (all 4 gone) when either every cell has gone terminal (`computeVacatedTrayIds`) or a successor tray is founded in the same carousel position (`computeTrayEvictionDates`). Note the split between *scheduling* and *display* of a fully-terminal tray: for scheduling (grid ghosts, box-collision) `computeVacatedTrayIds` frees its wells to load onto, but the **instrument tray overview** (`instrumentTrayMaps.computeInstrumentTrayMaps`, v0.34.8) deliberately does **not** consume `vacatedTrayIds` — it keeps a fully-terminal tray in its carousel slot rendered *depleted* (all cells "spent"/"expired", 0 uses) until a successor tray evicts it (`computeTrayEvictionDates`), because the physical object is still in the bay until an operator swaps it. So a used-up tray reads as a greyed-out resident on the overview even while its slot is a droppable "+" on the grid. A second, related nuance (v0.36.1): the overview's *default* view shows each cell's committed-plan state ("used up by end of week"), but its live **NOW** hover reconstructs physical reality via `usesRemainingAt`/`cellExpiryState` — counting only the uses whose staggered breakout (`BREAKOUT_STAGGER_H`) has actually happened by now. A cell the plan has already marked `exhausted` (its whole week scheduled, or a disposal set ahead) therefore reads as still holding a use in the NOW view until that use physically breaks out — so on today's run only the first cell reads spent while its siblings still show the use they're holding. (`window_expired`/`stopped`/`retired` cells never come back to life this way — capacity lost for a real reason.) **Any deliberate disposal action — manual "Discard all cells", or auto-disposal driven by the `max_uses` dial — must therefore operate on the whole tray, marking all 4 cells terminal together; disposing a strict subset of a tray's cells is physically impossible and must never be produced.** (`discard_tray()` already does this correctly for the manual action; the auto-fill path must match it — see the `max_uses` bullet below.) **The one and only way a single cell leaves service on its own — keeping its tray siblings live — is a QC stop (`stop_cell`, a hardware-fault signal); there is deliberately no "dispose one cell" action, because it's physically impossible to bin one cell of a 4-cell tray.**
- **Planning a tray disposal ahead of time — the reversible "skip reuse" flag (`CellTray.reuse_disabled_at`, v0.40.0).** The lab often *knows* it will bin a part-used tray before the disposal physically happens (e.g. a weekend run left a cell on Use 2/3, but next week's samples should open fresh cells rather than take the stranded 3rd use). Setting a tray's `reuse_disabled_at` makes `load_prior_cells()` (`services/engine_bridge.py`) drop every cell in that tray from the reuse pool, so **autoschedule and Recalculate stop offering it and fall back to fresh cells** — without first loading a sample and rotating/discarding a filled tray. Because the lab has declared it's binning the tray, `open_new_tray()`'s box-collision guard *also* treats a flagged tray's still-open cells as physically removed, so a **fresh tray can load into its carousel position** (the same "being removed" model an expired tray already uses) — without this, excluding the tray from reuse but still blocking its box would just strand the new samples unplaced, reproducing the very bug this feature fixes. It is **advisory and fully reversible**: unlike a real discard (`discarded_at`) it touches no cell status and cancels no uses, and clearing it (NULL) re-admits the tray to reuse. Toggled per-tray from the **Autoschedule drawer's "Reuse this week" list** (`POST /api/cells/skip-reuse-tray`; frontend `AutoscheduleReuseTrays`), and surfaced as a "Reuse skipped" badge wherever the tray's cells render. It's the *soft, planning* half of disposal — a real `discard_tray()` (physically binned) is the terminal half that later supersedes it. Whole-tray by construction (the flag lives on `CellTray`, not `Cell`), consistent with the all-or-nothing invariant above.
- **No shared tray-level expiry clock.** Each cell in a tray keeps its own independent 108h-from-its-own-first-use deadline (rule #2 above) — a tray is a grouping label over 4 independently-clocked cells, not a new deadline concept. Two cells in the same physical tray can start their clocks weeks apart, and the grid's per-slot expiry shading (`StageOut.window_hours_elapsed`) reflects each cell's own clock, never a tray-wide one.
- **The 3 unused siblings surface as preferred reuse candidates automatically, with zero engine changes**, because `load_prior_cells()` (`services/engine_bridge.py:41`) already selects every `Cell.status == "open"` row with no floor on `uses_consumed`, and `pack_cells()`'s sort key already puts every "prior" candidate ahead of opening a fresh one (rule #5 above). This directly implements the vendor's "reuse before new cell" priority *between trays*, not just within one.
- **`current_location()` (`cell_service.py:69`) falls back to the tray's instrument** for a cell with no active uses but a `tray_id` set — otherwise an unused sibling wouldn't know which instrument its physical tray is already sitting on, and would incorrectly be offered as free to land anywhere.
- **`pack_cells()`'s `available_days` cap now also bounds prior cells, not just fresh ones** (`engine/packing.py`) — without this, a single-day batch could plan all 3 of an unused sibling's remaining uses onto it, when only 1 could ever actually be placed that day (a cell can only be reused once per calendar day), stranding the other 2 samples as unplaced instead of spreading them across other cells that could take them today. This gap already existed in principle (a real prior cell with `remaining > 1` and only 1 day on offer), but eager tray population is what made it a routine occurrence instead of a rare edge case.
- **The `max_uses` dial ("Max uses per cell") is a per-cell TOTAL-use cap for *both* fresh and prior cells; reaching it triggers disposal of the cell's whole TRAY, never the individual cell** (`engine/packing.py::_prior_allowance`, `services/auto_fill_service.py`). `max_uses` counts total acquisitions (1st use + reuses), not reuses; it never exceeds `CELL_MAX_USES = 3`. `pack_cells()` plans a prior cell at most `max_uses - uses_consumed` further uses (previously prior cells were bounded only by physical `remaining`, so with a `1×`/`2×` dial a leftover open sibling could still be stacked to 3). Because a tray of 4 is one physical object (see the all-or-nothing invariant above), the dial governs *when a whole tray is spent* and disposal is tray-level: a tray is disposed — all 4 of its cells marked terminal together, via the same `discard_tray()`/`mark_cell_discarded` path the manual "Discard all cells" uses — only once **every** cell in it has been used to the dial (i.e. the tray is fully spent to the chosen depth). A tray still holding an unused or below-dial cell stays on the instrument, all cells `open`, for a later run to finish and then dispose as a unit. Disposed cells go terminal (`status="exhausted"`, sticky via `discarded_at`) and drop out of the reuse pool (`load_prior_cells()` selects only `status="open"`). Reported in the auto-fill result as `disposed_cell_ids` and surfaced to the user as "N cell(s) disposed".
  - Implemented in `auto_fill_service.py`'s post-placement pass: it collects every tray the run touched (via `touched_cells`/`opened_boxes`), and for each one bins the whole tray — `mark_cell_discarded` on all its cells at once — only when `all()` of its cells have `active_uses >= max_uses`; otherwise it leaves the tray untouched. Trays holding a stopped/retired cell are skipped (they need manual attention), and cells already terminal by natural exhaustion (dial == 3) aren't re-flagged or counted, so `disposed_cell_ids` reports only capacity deliberately binned early (dial < 3). Covered by `tests/integration/test_auto_fill_api.py` (`test_auto_fill_disposes_a_tray_once_all_its_cells_reach_the_dial`, `test_auto_fill_leaves_a_partly_used_tray_open`).
- **A tray-linked cell that goes back to 0 uses (a placement removed/cancelled/re-cancelled) is never deleted as an "orphan placeholder" on its own**, unlike a legacy non-tray cell (`placement_service.py`'s `remove_sample()`/`move_sample()`/`cancel_run()` all key this off `cell.tray_id is None`) — it's a real physical sibling and stays open/reusable *as long as at least one cell in its tray still has real use history*. But if that was the tray's only real use anywhere — every one of its `CELLS_PER_TRAY` cells now sits at 0 uses — the whole `CellTray` and all its `Cell` rows are deleted too (`cell_service.cleanup_tray_if_fully_unused()`, called from the same three sites). Without this, undoing an entire never-confirmed plan (Clear schedule, or deleting every sample in a tray) left a "ghost" tray with reserved cell IDs and no samples lingering in the weekly grid for the rest of the week, with no way to clear it — reported as a bug once eager tray population made an all-zero-use tray common instead of rare. The cutoff for "real use history" is any `CellUse` row at all (including a stopped cell's permanent `cancelled` marker, not just active ones) — only genuinely untouched siblings get swept away.
- **Bootstrap cutover cells (`bootstrap_cell()`) have no tray** — there's no way to know a historical cell's real sibling history, so `tray_id`/`tray_position` stay null for them, same as for any cell created before this feature shipped.
- **Every sibling is pinned to a well the moment its tray opens, via `Cell.home_well`** (migration `c7f3a1e9d5b2`) — `open_new_tray(db, instrument_id, well)` now takes the well the sample is landing in right now, derives which 4-well box of `WELLS` it belongs to (tray 1's `A01-D01` or tray 2's `A02-D02`), and assigns each of the 4 siblings a `home_well` from that box in fixed order. `current_location()` returns `cell.home_well` (not `None`) for a cell with no active uses but a tray set, so an unused sibling surfaces a real `current_well` through `CellOut` just like a used cell would — this also transparently activates the existing "must stay in its own well" guard shared by `place_sample()`/`move_sample()` (`placement_service.py::_resolve_cell_choice()`), no new validation needed.
- **Grid rendering model (v0.12.0 — see "Plate vs cell" above): a grid slot is a plate LOADING position, not a cell.** Every empty, unlocked slot renders as a plain droppable **"+"** — a used-up cell no longer blocks its slot. Dropping a sample onto it resolves server-side to the next-usable cell in that carousel position (reuse-before-new, `derive_best_cell`); no `ghostCellId` is threaded onto the drop and no drop-time picker appears (`SchedulerSlot.DroppableSlot`, `useSchedulerDnd`). The chosen cell is shown only afterwards, by the loaded card's stub.
  - A well holding a **terminal** cell (exhausted/window_expired/retired) is **no longer a non-droppable ✕ "spent well"** — that block was removed. The slot is an ordinary "+"; the drop routes to a sibling with capacity, or opens a fresh tray once the whole tray is spent. `computeTerminalGhost()` and its slot-blocking plumbing were retired. The amber warning banner next to Confirm loaded (`computeCellExpiryWarnings`) is now the only place a cell's forward-looking expiry surfaces on the grid.
  - **The waste warning is per-CELL 108h expiry, not per-tray disposal** (reported by the lab owner: "a tray as a whole doesn't expire, only its cells do — warn of expiring cells, not expiring trays"). `computeCellExpiryWarnings` (renamed from the former `computeTrayDisposalWarnings`) flags each *open, already-used* cell (`uses_consumed > 0`, capacity left) on its own 108h reuse cutoff day, showing the cell, well, and uses it would strand — one line per cell. A **never-yet-used** tray sibling has no 108h clock (the clock starts at first use) and is **never** flagged: a physical tray has no lifespan of its own. This dropped the old model's `evictedBySuccessor` "(new tray loads next)" framing and its counting of never-used siblings as "wasted"/"disposed". A cell's cutoff is still bounded by `computeTrayEvictionDates` (a successor tray in the same carousel position), because **trays remain disposed-on-removal for now** — reloading a partly-used tray later is a deliberate *future* capability the lab owner flagged, not yet modelled; when it lands, the eviction bound on the cutoff can drop and a cell's cutoff becomes purely its 108h window. Covered by `waitingCells.test.ts`'s `computeCellExpiryWarnings` suite.
  - The remaining non-droppable ✕ is a **QC-stopped** cell (`stop_cell`): its exact well stays a permanent marker for the rest of that tray's tenure (`computeBlockedWellsByInstrumentAndDay`). This is a hardware-fault signal, distinct from routine turnover.
  - `CellChoicePicker`/`useCompatibleCells`/`cellChoiceGate`'s `wellConflict` machinery is dead: a plain drag (place or move) never shows a picker — the backend keeps or derives the cell.
- **Physical-cell identity is shown by a holographic "security seal" on each loaded card's right-edge stub** (`SchedulerSlotView`): the stub keeps its well-letter + use-number label (e.g. `A2`) and Use 1/2/3 base colour, and adds an iridescent sheen hue-rotated per `cell_id` (golden-angle spread) plus the cell's own short id as repeating vertical microtext. **Bug found and fixed (reported: dragging a placed sample from one tray position to the same tray position on a different day made the sample keep its own original cell instead of adopting whatever cell truly lives in that slot, and the destination's real cell appeared to "move" to the day the sample came from):** `move_sample()` (`placement_service.py`) decided whether to reassign a moved sample to a different cell purely by comparing the destination well against wells recorded on the cell's own *other* `CellUse` rows (`other_uses`). Covered by `tests/integration/test_move_endpoint.py::test_move_to_a_different_slot_same_day_requires_cell_choice_for_the_resident_sibling` and `test_move_onto_a_well_whose_tray_has_since_turned_over`. **The narrower gap left open at the time** - a cell with no other uses yet being moved to a *different instrument* freely, without updating its pin - was closed separately afterward; see `test_move_across_instruments_reassigns_to_a_new_cell_even_as_the_cells_only_use` and the `pinned_serial` fallback in `move_sample()`.

**Bug found and fixed (reported 2026-07-26: dragging a sample onto a plate slot on a date the carousel position's current tray had already expired did nothing — a silent rejection):** the drop resolved correctly to "mint a new tray" (`derive_best_cell` refuses to reuse an out-of-window cell — `_reuse_window_open` checks the 108h deadline against the *target acquire_date*, so a future date past the window drops every resident cell from the reuse candidates and falls through to `{"mode":"new"}`), but `open_new_tray`'s box-collision guard then raised a 409 because that same expired tray's cells are still persisted `status == "open"`. The two computations disagreed on what "expired" means: `recompute_status`/`window_breached` (`cell_service.py`) only flips a cell to `window_expired` once *real* "now" passes the deadline **and** the cell was Confirm-loaded (`first_use_started_at` set) — a forward-planned tray whose first use was never confirmed keeps its cells `open` indefinitely, so the box guard treated the position as still physically occupied and refused to reload it. **Bug found and fixed (reported 2026-07-27: dragging a barcode-clashing sample onto a reuse day silently produced an impossible cell order on the plate — "cell order 3 then 2" across the loading slots, with no error):** a plain drag resolves its cell via `derive_best_cell`, which treats a grid slot as a pure *loading position* and reaches for the next-in-order *eligible* cell regardless of which slot it was dropped on (`_pick_next_reuse_cell`; deliberate — see the "Plate vs cell" model and `test_auto_place_reuse_picks_the_next_in_order_cell_not_the_slot_position`). Its barcode-clash check (`_reuse_eligible`, line ~439) is a **silent boolean**: a cell whose burned barcodes clash with the sample is skipped with no signal. So when the cell that would naturally back a slot clashes, the sample is silently handed a *later-tray-position* sibling, and a subsequent non-clashing drop then takes the skipped lower-position cell in a *later* slot — transposing two equally-reusable cells so the plate loads e.g. ▣2 in slot A01 and ▣1 in slot B01, which the instrument never does on a tray whose cells are all at the same use (it breaks cells out strictly A→B→C→D). The lab owner reported the ▣3-before-▣2 transposition and asked that it either reorder to a valid layout or **error** — but when the clash forces the sample off its natural cell, no valid ascending layout exists given the user's slot choices, so the honest outcome is to refuse. **Fixed (v0.16.6)** by `placement_service._assert_no_barcode_forced_inversion(db, cycle_id)`, run after each place/move flushes its `CellUse` but before commit (in `place_sample`, `move_sample`'s same-cell reschedule, and `_move_sample_to_new_cell`; the caller rolls back on the raise so nothing is persisted). It scans the destination plate for two stages of the *same tray* whose loading-slot order (`within_tray_pos(well)`) and cell tray-position order (`within_tray_pos(home_well)`) disagree, and raises a 409 naming the culprit sample **only** when the two cells are at the **same reuse depth** (`derive_cell_state(...)[0]` equal — a genuine depth/expiry difference is the documented "most-used / expiring-next first" ordering, or the lab owner's noted *shorter-run* exception, and is left alone) **and** the transposition is barcode-forced (the earlier-slot sample's barcodes clash with the later-slot, lower-position cell — i.e. it genuinely couldn't have taken that cell). The earlier-slot sample is always the culprit regardless of drop order, so the message names it either way. The query uses `populate_existing=True` because a sibling cell last loaded in an earlier committed request can otherwise carry a stale `cell_uses` collection, giving `derive_cell_state` a wrong use count and mis-firing the depth exception. The error surfaces via the existing `removeSlotsError` Note (frontend unchanged). Covered by `tests/integration/test_clash_forced_inversion.py` (block, block-regardless-of-drop-order, the reuse-depth-difference exception is allowed, and an ordinary no-clash plate is unaffected). **Superseded below (2026-08-05)** - the block-on-inversion approach itself turned out to have a gap wide enough to reproduce the exact symptom it was meant to prevent; see the entry immediately following.

**New rule, replacing the fix above (reported 2026-08-05): sequential samples in a plate always take sequential cells from a tray - a barcode clash is a warning, never a reason to skip a cell or block a drop.** The lab owner reported the *exact* "impossible cell order" symptom the 2026-07-27 fix above was supposed to have closed: a sample dropped onto a well with a barcode clash kept that well but was scheduled onto a later, out-of-order cell, with no error. Root cause: `_assert_no_barcode_forced_inversion` is *pairwise* - it only ever compares two already-committed stages on the same plate, so the very first clash-forced skip in a cycle (a lone drop, nothing yet on the plate to compare it against) sails through uncaught; only a *second*, sibling drop that would complete the visible transposition ever tripped the 409. A single manual placement - the common case, and exactly what was reported - was never covered.

Rather than widen the pairwise check to also catch a lone skip, the fix removes the root cause instead: **`_reuse_eligible` (`placement_service.py`) is no longer barcode-aware at all.** A tray breaks its cells out in a fixed physical order that the instrument itself cannot reorder around a demultiplexing concern - so for a manually-dropped sample, the cell chosen for a given well is now *always* whichever the instrument would actually reach for next (reuse-before-new, most-used-first, then tray position), full stop. A barcode clash is never again a reason to reach past that cell for a different one - which also means the pairwise transposition `_assert_no_barcode_forced_inversion` guarded against is now structurally impossible via this path (nothing can force a skip, so nothing can transpose two cells), and that function has been removed entirely along with its 409.

The clash itself is not hidden - it's real, and it is surfaced, just never by rerouting or blocking:
- The placed `CellUse` is flagged via the same mechanism a Cell-QC re-zip has always used - `cell_service.has_barcode_clash()` / `StageOut.barcode_clash` - so the existing hazard-striped "⚠ Clash" card marking and the Slot Detail popover's warning `Note` now also fire for this far more common cause, not just the rare QC re-zip case they were originally built for (their copy was broadened accordingly to stop implying QC re-zip is the only way to see them).
- **New, additive UX**: while dragging a sample, every empty slot whose natural next-in-order cell would clash with it lights up with a dashed red "danger zone" warning - a best-effort client-side preview (`waitingCells.ghostWouldClashWithSample`), not authoritative (it can't see the exact per-barcode owner the backend can, only the cell's aggregate burned barcodes and use history), so it undersells or oversells a rare edge case rather than blocking anything. The drop still succeeds regardless; the authoritative answer is always the post-drop card marking and popover note.
- At the time of this fix, one place still hard-blocked a clash: an *explicit* `cell_choice` naming a specific cell (`_resolve_cell_choice`) and `swap_samples`. **That last block was removed on 2026-08-07 — see the next entry; a barcode clash now warns, never blocks, on *every* manual path.**

This does **not** loosen the burned-barcode carryover rule described below for the case that rule actually protects. It only stops the ordering algorithm from treating a clash as a reason to hand a manually-dropped sample a *different, out-of-order* cell than the one the tray would really give it - an outcome that was never actually safe (it produced an impossible plate order), just silently plausible-looking. Covered by `tests/integration/test_barcode_clash_placement.py` and `tests/integration/test_auto_derive_cell.py::test_auto_place_reuses_a_clashing_cell_rather_than_skipping_it`.

**Sequential wells take sequential cells, enforced by re-sequencing the whole plate on every drop (reported 2026-08-07).** The lab owner reported the "cell number went out of sync" symptom the 2026-08-05 fix above did not fully close: a manually-dropped sample could still leave a plate reading an out-of-order cell number (e.g. `A=1, B=4, C=3, D=2`), and dragging a card between wells made its cell number jump. Root cause: the 2026-08-05 fix made *cell selection* correct (reuse-before-new, never skip a cell for a clash) but nothing ever *re-laid the plate's wells onto its cells in order* afterward. A grid slot is a plate LOADING position and the physical cell backing it is picked independently (`_pick_next_reuse_cell`, slot-blind), so out-of-order population (drop A, then C, then B) or a well-to-well move left the displayed cell numbers (`Cell.tray_position`, the `▣N` stub) non-ascending across the wells — and `move_sample`'s old `exclude_cell_id` reassignment forced a moved sample onto a *different* physical cell, so its number changed on the move.

**The model, lab-owner decision:** within one plate, the occupied wells read in order (A→B→C→D) must always be backed by the plate's cells in reuse-priority order (**expiring-first, then tray sequence 1,2,3,4** — the same `_reuse_priority_key` selection already used, `(-consumed, first-use-start, tray_position)`). Every drop takes the **next-available cell regardless of the plate well it lands on** (so a lone drop onto C01 of a fresh tray runs on cell 1, not the position-matched cell 3 — `_fresh_tray_cell`); inserting a sample in an earlier well **re-sequences** the later ones (drop A, then C=2, then B → A=1, B=2, C=3). This intentionally **re-tightens** the "loading position ≠ cell identity, and the two may diverge freely" render of the v0.12.0 "Plate vs cell" model below: the physical-independence of cell trays and sample plates (cross-box reuse, a cell pinned to its tray position for life) is unchanged, but the *displayed* well→cell-number mapping within a plate is now always ascending. When the tray is used evenly (the norm — a run advances all four cells in lockstep) "expiring-first" and "ascending tray position 1,2,3,4" coincide; they only diverge in a rarely-reachable unevenly-used tray (e.g. after a QC stop), where "expiring-first" wins by the lab owner's choice and the earliest well may show the more-used cell.

**Implementation (`placement_service.py`):** `_resequence_plate(cycle)` is a pure permutation of a still-`planned` plate's existing cells across its existing wells (each cell keeps exactly one use on the plate, so its consumed count / priority is invariant under the remap — the order is computed once and is stable). It is called after every place / move / removal that can change a plate's set of wells or cells (`place_sample`, `move_sample`'s same-plate fast-path and same-cell reschedule, `_move_sample_to_new_cell`, `_remove_one`). It queries `CellUse` directly (not `cycle.cell_uses`) because callers reach it right after a raw `cycle_id` insert whose ORM collection is stale, the same reason `recompute_cycle_timing` does. A confirmed/loaded plate is never touched. `move_sample` gained a **same-plate fast-path** (a within-plate reorder just moves the loading well and re-sequences, no cell churn) and **dropped the `exclude_cell_id` workaround** entirely — a moved sample may now re-adopt its own cell, since re-sequencing enforces ascending order regardless.

**And the last clash hard-block was removed (2026-08-07): a barcode clash now warns, never blocks, on *every* manual path.** `_resolve_cell_choice` (explicit "existing" pick) and `swap_samples` no longer raise the `"barcode conflict"` 409 — the placement/swap lands and the clash is surfaced on the card (`StageOut.barcode_clash`) for the user to rectify, exactly as a plain drag already did. The lab owner's rationale: a clash can be acceptable (e.g. the same sample), so the app must warn and let the user decide, never physically prevent a manual placement. Capacity (the 3-use cap) and the 108h window remain **real** blocks — distinct from a clash. The now-dead frontend "rejected drop" clash-flash (`clashSlotKey`/`clashFlash`) was removed along with it; the persistent hazard-striped "⚠ Clash" card marking + Slot Detail note are the authoritative signal.

**Serializer fix in the same change:** `run_serializer._use_number` now ranks a cell's uses over `active_uses` (non-cancelled) only, so a cancelled "Blocked" Stop-cell marker sitting chronologically between two real uses no longer inflates a later use's number (it used to render "Use 3 of 3" — even "Use 4 of 3" — on a cell with 2 real uses). Covered by `tests/integration/test_plate_resequencing.py` (out-of-order drops re-sequence; the forbidden descending state is unreachable; lone later-well drop takes cell 1; a move keeps the plate ascending; a second run's C+D reuses the first-expiring cells ascending) plus the updated `test_barcode_clash_placement.py` / `test_placement_api.py` / `test_swap_endpoint.py` / `test_cell_reuse_across_placements.py` / `test_duplicate_barcode_reuse.py` / `test_move_endpoint.py` warn-everywhere and re-sequence assertions.

## App-level invariant: a cell can never move between instruments

This is not sourced from the PacBio deck — it's a scheduling invariant specific to this app's model of a physical cell's lifecycle, worth documenting explicitly because it's easy to assume "packing" logic is free to reassign a reusable cell wherever a slot is open.

**Once a `Cell` has a real (non-cancelled) `CellUse`, every subsequent use of that same cell is confined to the instrument it was first used on — for the lifetime of that cell, across both manual placement and autoschedule ("auto-fill"), regardless of how many instruments are selected/offered.** A cell with no prior use is unpinned and free to land on any offered instrument for its first use; once placed, it's pinned for good.

**This is a claim about the physical `Cell`, not about a planned `Sample`.** A recurring point of confusion (worth stating plainly, since it drove real design questions about drag-and-drop): a sample isn't physically loaded onto anything until its run actually executes — the instrument itself is what moves it from its plate onto a cell, at run time. Before that, a sample sitting in an unexecuted `CellUse` is pure planning state. So "a cell can never move between instruments" does **not** mean a planned sample is stuck wherever it was first scheduled — dragging a placed-but-not-yet-run sample onto a different instrument is just re-planning, and always resolves to a (possibly new) physical cell on the destination instrument, never to relocating the original cell. See `move_sample()`'s cross-instrument reassignment below, which implements exactly this: the sample moves freely; the physical cell it was on stays exactly where it was pinned, untouched, available for whatever other uses it still has.

This is enforced at every layer that can assign a cell to an instrument, not just one gate:
- `services/cell_service.py::current_location()` (`cell_service.py:69-76`) derives a cell's pinned instrument from its most recent active `CellUse` → `Cycle` → `RunBatch` → `Instrument.serial_number`. A `Cell` has no direct FK to `Instrument`; location is always derived, never stored, so there's no stale pin state to fall out of sync. "Most recent" is by the use's actual `run_date` (via `use_run_date()`, `cell_service.py:58-66`), not `CellUse.id` — see the bug note below.
- `services/placement_service.py::place_sample()` (`placement_service.py:164-170`) — manual/drag-drop placement — raises a 409 if a cell's current instrument doesn't match the target instrument (there's no existing placement to reassign here, so a genuine cross-instrument attempt at this specific call is just a bad `cell_choice`, not a move). `move_sample()` (`placement_service.py:438-467`) instead treats a destination-instrument mismatch as a trigger for reassigning the *sample* to a different cell (see below) — never a hard rejection — since a drag-move always has a sample to re-plan onto a fresh cell, unlike a raw `cell_choice`.
- `engine/slot_scheduling.py::fill_slots()` (`slot_scheduling.py:68-69`) — the auto-fill packing loop — skips any slot whose instrument doesn't match `cell.pinned_instrument_serial`, falling the sample to `unplaced` rather than crossing instruments even when a slot elsewhere is free. As of the fix below, it also *sets* `pinned_instrument_serial` (`slot_scheduling.py:95-96`) the first time an until-then-unpinned cell is actually placed, so the pin check above also constrains a fresh cell's 2nd/3rd use within the same batch, not just prior cells loaded from the DB. This restriction is unchanged by the manual-move fix above — one Auto Schedule batch still never spreads a single cell's uses across instruments; only interactive drag-and-drop of one already-placed sample gained the ability to cross instruments.
- `services/auto_fill_service.py::auto_fill()` (`auto_fill_service.py:96-104`) pre-filters the reuse candidate pool before packing: a prior cell pinned to an instrument outside the currently-selected/offered set is excluded entirely, so it can't "claim" a sample via barcode compatibility only to strand that sample once `fill_slots` rejects the cross-instrument placement.

Covered by unit tests in `tests/unit/test_slot_scheduling.py`: `test_fill_slots_respects_cross_instrument_pin_when_a_compatible_slot_exists`, `test_fill_slots_strands_pinned_cell_when_only_a_different_instrument_slot_is_offered`, `test_fill_slots_unpinned_cell_can_use_any_offered_instrument` (confirms fresh cells remain free to land anywhere), `test_fill_slots_pins_a_fresh_cell_to_its_first_assigned_instrument`, and `test_fill_slots_fresh_cell_reuses_stay_on_first_instrument_when_available`; end-to-end via `tests/integration/test_auto_fill_api.py::test_auto_fill_keeps_a_reused_cell_on_one_instrument_when_multiple_are_offered`.

**Bug found and fixed (reported: auto-schedule with every instrument selected put one cell's Use 1/2/3 on three different instruments):** `fill_slots()` only ever *checked* `pinned_instrument_serial`, it never *set* it for a cell with no prior DB use — `PackedCell.pinned_instrument_serial` defaults to `None` for a freshly-created cell (`engine/packing.py`'s "open a new cell" branch never passes it), and nothing updated it as that same cell's uses got assigned across a multi-day, multi-instrument batch. So a fresh cell's Use 1 could land on instrument A, Use 2 on instrument B, Use 3 on instrument C, all within one Auto Schedule click — the "once placed, it's pinned for good" sentence above was aspirational, not enforced, for this one case. Fixed by pinning the cell to its first assignment's instrument at the point of placement (`slot_scheduling.py:95-96`).

A second, compounding bug made the symptom look even more broken ("second use" appearing to be scheduled *before* "first use"): the Use 1/2/3 label (`services/run_serializer.py::_use_number()`) and several `cell_service.py` helpers (`current_location()`, `last_use_run_date()`, `first_use_planned_start_at()`, `serialize_cell_detail()`) all ordered a cell's uses by `CellUse.id` (DB insertion order) under the assumption that insertion order tracks chronological (`run_date`) order. That assumption breaks once a cell's uses span more than one instrument, because `auto_fill_service.py`'s persist loop (deliberately, for an unrelated reason — detecting same-batch instrument locks) inserts `CellUse` rows sorted by `(instrument_serial, run_date)`, not chronologically. Fixed by deriving order from each use's actual `run_date` (new `cell_service.py::use_run_date()` helper, `cell_service.py:58-66`) everywhere a cell's uses need chronological ordering, with `CellUse.id` only as a tie-break. `placement_service.py::move_sample()`'s own pin check (`placement_service.py:352`) got the same fix.

A third, unrelated bug surfaced only after the two fixes above changed exactly when `Cell.cell_uses` first gets lazy-loaded during response serialization: `move_sample()` was moving a `CellUse` to a new `Cycle` by writing the raw FK (`cell_use.cycle_id = dest_cycle.id`) instead of going through the ORM relationship. `Cycle.cell_uses` is `cascade="all, delete-orphan"` (`models/schedule.py`'s `Cycle` model), and a raw FK write bypasses SQLAlchemy's collection-membership tracking that cascade depends on — under the right relationship-loading timing, the unit of work concluded the row had been orphaned from its old `Cycle` and deleted it outright, silently losing the moved placement (empty `stages` in the response). Fixed by assigning through the relationship instead (`cell_use.cycle = dest_cycle`, `placement_service.py:389`), which keeps both sides of the `back_populates` pair in sync and gives the cascade an unambiguous "moved to a new parent" signal instead of an ambiguous "orphaned" one. This class of bug is specific to `Cycle.cell_uses`'s `delete-orphan` cascade; `Cell.cell_uses` (`models/cell.py`) has no such cascade, so a raw `cell_id` FK write is safe there.

**If this ever needs to change** (e.g. to support an operator physically relocating a multi-use cell to a different instrument), it requires a deliberate design decision, not a one-line relaxation: `slot_scheduling.py:68-69,95-96` and `auto_fill_service.py:101-104` would both need to relax together, `placement_service.py:165` would need an explicit override path, and `current_location()`/`pinned_instrument_serial` would need a defined meaning for "reassignment" — today the model has no way to represent a cell moving mid-lifecycle short of falsifying its `CellUse` history. This paragraph is specifically about the *engine* (auto-fill's `fill_slots`/`auto_fill_service`) and about `place_sample`'s raw `cell_choice` path — it is unaffected by the manual drag-and-drop fix below, which only ever reassigns a *sample* to a fresh cell, never relocates a `Cell` row itself.

**Bug found and fixed (reported: dragging a placed sample onto a different instrument was flatly rejected, and — the more serious half — dragging a cell with no other uses yet onto a different instrument silently succeeded by rewriting its existing `CellUse` onto the destination instrument's cycle, corrupting the cell's own derived pin):** this closes the gap the previous bug note above deliberately deferred. `move_sample()` decided whether to reassign a moved sample to a different cell using only two signals: a well mismatch against the cell's *other* uses, and (after the fix above) a different resident cell already sitting in the destination well. Neither signal ever looked at the *destination instrument* itself. A cell with other uses pinning it elsewhere got a hard 409 if the destination instrument differed (`"Cell {code} is already in use on instrument {pinned}; cannot move it to {instrument}"`) — correct in spirit (the physical cell really can't go there) but wrong in response: a sample isn't physically loaded onto anything until its run executes (see the clarifying paragraph above), so this should reassign the sample to a new cell, not refuse outright. Worse, a cell with *no* other uses yet skipped the instrument check entirely (the check was nested inside `if other_uses:`), so the code fell through to the in-place update and silently moved that `CellUse` onto the destination instrument's `Cycle` — the physical cell's `CellTray.instrument_id` never actually changed, so `current_location()` would then derive a pin that disagreed with where the cell's own tray really was. Fixed by computing the cell's pinned instrument unconditionally (falling back to this very use's own run batch when there are no other uses, since that's the only placement that has ever pinned it anywhere) and treating *any* instrument mismatch — with or without other uses — as a trigger for the same `_move_sample_to_new_cell()` reassignment path the well-conflict case already used, never a rejection. `CellChoicePicker.tsx`'s `wellConflict` got the matching fix: two different instruments' grids reuse the same well-label set (e.g. both have an `"A01"`), so a well-string match alone never proved the drop was staying on the same physical cell — `wellConflict` now also fires whenever the drag's source instrument differs from the drop's destination instrument. Covered by `tests/integration/test_move_endpoint.py::test_move_across_instruments_reassigns_to_a_new_cell_when_cell_has_another_use` and `test_move_across_instruments_reassigns_to_a_new_cell_even_as_the_cells_only_use`.

**Bug found and fixed (reported: Auto Schedule on one instrument for a full working week with "Cells per day" set to 4 put 5 uses on one physical cell — one more than the hard 3-use cap):** `fill_slots()` rebuilds `free_wells` fresh for every calendar day, so a well a fresh cell claimed on Monday shows "free" again on Thursday the moment that cell's own pack-assigned quota runs out (e.g. it hit its individual 3-use cap by Wednesday) or it's simply not reused that day. Nothing stopped that "vacated" well from being handed to a *different*, brand-new `PackedCell` for the rest of the batch — each individual `PackedCell` still honored the 3-use cap on its own, but `auto_fill_service.py`'s persist loop resolves a well back to whichever physical `Cell` its box was first opened with (`opened_boxes`, keyed only by `(instrument, box)`, not by which logical packed cell is entitled to a given well), so two unrelated `PackedCell`s landing in the same well (Mon–Wed for the first, Thu–Fri for the second) silently stacked onto the *same* real `Cell` row — 3 + 2 = 5 real `CellUse` rows on one cell. This is specific to `cells_per_day=4`: with tray 2 also open (the default, 8), a full-tray run's lock spills into the next day (see "Instrument load-lock timing" below) often enough that this exact midweek-exhaustion-then-reopen window doesn't line up, which is why it went unnoticed.

Fixed in two layers, since a first pass that only addressed the overuse over-corrected into refusing to ever reload a genuinely spent well within one batch (reported as a follow-up: "auto-schedule now stops after day 3 across the board — day 4 should open a new tray, reused day 5"), which is explicitly legitimate (`open_new_tray()`'s own docstring: "a box whose every cell has gone terminal is not a collision... a brand-new tray can be loaded into it again"):

- `slot_scheduling.py`'s `well_owner` map (`slot_scheduling.py:49-83,121-127,154-156`) is seeded up front with every cell that already has a real, known physical position (prior cells from `engine_bridge.load_prior_cells`), and updated the moment a freshly-opened cell first claims a well. A well already claimed by a *different* `PackedCell` is only offered to a new one once `_well_is_vacated()` confirms the current owner has truly finished — its lifetime total (`total_uses`, already computed by `pack_cells`) has hit `CELL_MAX_USES` *and* every one of its batch-planned uses has actually been placed. A cell `pack_cells` only gave partial work to this batch (e.g. `total_uses` is 1 or 2 — the backlog simply ran out of compatible samples for it, not because it's spent) keeps its well reserved indefinitely, since it may still get reused in a *later*, separate Auto Schedule call and that must land back in the exact same well.
- `auto_fill_service.py`'s persist loop (`auto_fill_service.py:163-172,238-268`) mirrors this at the DB level with a `well_claimant` map, tracked *per well* (not per box — several different fresh `PackedCell`s legitimately share one box at once, one per well). When a different `PackedCell` needs a well the engine has already proven vacated, the loop recomputes the old box's 4 cells' status right then (rather than waiting for this function's own end-of-loop pass) and retires the cached box, so `open_new_tray()`'s own DB-level "is this box still live" collision guard sees them as already exhausted and allows the legitimate reopen — if some sibling in the box genuinely *hasn't* finished (an uneven-quota edge case), that same guard correctly refuses the reopen and the sample is left unplaced rather than corrupting anything. This needs an explicit `db.flush()` right after the `recompute_status()` calls: this project's session runs with `autoflush=False` (`db.py:42`), so without it the status changes stay pending Python-side and the collision guard's own raw query wouldn't see them yet.

`open_new_tray()`'s own DB-level box-collision guard already catches the equivalent mistake *across* two separate Auto Schedule calls (a later call's fresh cell correctly gets refused a well an earlier, still-`open` real cell owns) — the gap was purely within one single call's in-memory plan, before any status had a chance to be recomputed.

One known residual gap, left as a follow-up rather than folded into this fix: `pack_cells()` assigns every fresh cell a flat `min(max_uses, available_days)` depth with no awareness that a *second-generation* cell reloaded mid-batch only has however many days are left after the first generation's wells free up, not the full `available_days` count — so it can over-commit a reloaded cell to 3 planned uses when only 2 days actually remain, leaving a couple of samples honestly reported unplaced rather than repacked onto one more fresh cell that could have taken them. Safe (never over-uses or drops anything silently), just not perfectly optimal; would need pack_cells and fill_slots' day-accounting to be merged to close fully.

Covered by `tests/unit/test_slot_scheduling.py::test_fill_slots_never_hands_a_vacated_well_to_a_different_fresh_cell` and `test_fill_slots_reloads_a_genuinely_exhausted_well_with_a_new_cell`, and `tests/integration/test_auto_fill_api.py::test_auto_fill_never_exceeds_the_hard_three_use_cap_with_cells_per_day_four` and `test_auto_fill_reloads_a_terminal_well_with_a_new_tray_in_the_same_batch`.

**Bug found and fixed (reported 2026-07-31: a full working week selected on one instrument, "1 plate" (cells_per_day=4) and "Max uses per cell" dialed to 2x, placed only 8 samples - 2 days' worth - and left the other 3 selected days completely empty, with 0 cells reported skipped and 30+ fully compatible backlog samples left unplaced):** this is exactly the residual gap the line above warned about ("if Auto Schedule is ever reported hitting the same starvation despite a wide user-selected range") - except the cause wasn't a silently-narrowed selection (skipped_cells was genuinely 0; all 5 days really were offered). `_well_is_vacated()` gated reuse of a well on `total_uses >= CELL_MAX_USES` - the *physical* 3-use cap - not on whether the cell was actually done with what *this batch* intended for it. A dial set below 3 means a fresh cell's own `future_uses` (capped by pack_cells at `min(max_uses, available_days)`) can legitimately finish well short of `CELL_MAX_USES`, on purpose - but the old check couldn't tell that apart from "the backlog ran out of compatible samples for it" (the one case where a well must stay reserved indefinitely - see the fix above). So with no prior cells and `cells_per_day=4`, exactly `cells_per_day` physical cells could ever open in one batch: once they reached the dial, every one of the day's well positions was still "spoken for" by a cell the engine believed might come back, and nothing could open a 5th cell - capping the ENTIRE batch at `cells_per_day * max_uses`, invariant to how many days were actually offered (confirmed by direct reproduction: offering 10 weekdays instead of 5 placed exactly the same 8).

**Fixed** by adding `PackedCell.batch_capacity_reached` (`engine/types.py`), computed once in `pack_cells()`'s finalize loop as `future_uses >= (cap for a fresh cell, or _prior_allowance(c) for a reuse candidate)` - both formulas already governed the packing loop's own `cands` gate, so this only records a fact pack_cells already established, never changes what it packs. `_well_is_vacated()` (`slot_scheduling.py`) now requires this flag instead of the physical cap: a cell that stopped on its own batch-specific ceiling frees its well for a different cell later in the same batch; a cell that stopped short of that ceiling (backlog scarcity) still doesn't, unchanged from the fix above. On the persistence side, `auto_fill_service.py`'s tray-scoped auto-dispose logic (`_dispose_tray_if_fully_used`) - previously only run once, at the very end of the whole batch - was factored out and *also* called inline the moment the persist loop's collision-retirement branch needs a dial-exhausted box back, since `open_new_tray()`'s DB-level guard only ever treats a cell as available once its status has actually left "open", and `recompute_status()` alone never does that for a dial below the physical cap (only real exhaustion or window-expiry flip it). The end-of-batch sweep still runs too, idempotently, for any tray that reached the dial without ever being fought over mid-batch (e.g. the last generation of a week, with nothing left in the batch to reclaim its well) - it must still be disposed so a *later*, separate Auto Schedule call sees an open box to reload rather than a stale full tray.

One known residual gap, shared with (not introduced by) the fix above: a reloaded generation's own depth is still the flat `min(max_uses, available_days)`, not narrowed to however many days are actually left once its well frees up mid-week - so the last generation a wide selection opens can still be over-committed and leave a couple of samples honestly unplaced rather than repacked (see the "One known residual gap" paragraph above; would need the same pack_cells/fill_slots day-accounting merge to close for both at once).

Covered by `tests/unit/test_slot_scheduling.py::test_fill_slots_reloads_a_dial_capped_well_with_a_new_cell_even_below_the_physical_max` and `tests/integration/test_auto_fill_api.py::test_auto_fill_below_the_physical_cap_still_reloads_a_new_tray_mid_batch`.

## Rules worth mirroring in validation/messaging (not fully enforced yet)

- **Barcode carryover between uses is real, just small.** PacBio quantifies it: "Revio SPRQ-Nx use-to-use barcode carryover level is typically <0.1%" (p.19 footnote) — non-zero, which is exactly why this app's burned-barcode conflict guard exists. This is a stricter, zero-tolerance rule than PacBio's own instrument (which tolerates the <0.1% and demultiplexes anyway) — a deliberate safety margin, not a bug; don't loosen it without weighing that tradeoff explicitly. **Where it still hard-blocks: only the Auto Schedule / Recalculate *engine* (`engine/packing.py::pack_cells` excludes a prior cell whose burned barcode a candidate sample shares — `test_pack_excludes_prior_cell_when_sample_shares_a_burned_barcode`, `tests/unit/test_packing.py`).** Auto-generating a plan has full freedom to pick a different cell, so avoiding a clash there costs nothing. **Manual placement no longer blocks a clash on any path (2026-08-07): warn, don't block, everywhere** — a plain drag, an explicit `cell_choice`, and `swap_samples` all place/swap and flag the clash (`StageOut.barcode_clash`) for the user to rectify. See the "Sequential wells take sequential cells" entry above; `test_place_sample_flags_barcode_conflict_on_existing_cell_but_does_not_block` (`tests/integration/test_placement_api.py`) and `test_cell_with_remaining_capacity_is_reused_across_days_and_burned_barcodes_respected` (`tests/integration/test_cell_reuse_across_placements.py`).
  - **History (2026-08-05, since superseded 2026-08-07): the auto-derive path stopped treating a clash as disqualifying.** A manually-dropped sample's well fixes which physical cell the tray would give it - there is no *different* cell to fall back on without producing an impossible plate order - so `_reuse_eligible`/`derive_best_cell` are barcode-blind. On 2026-08-05 the *explicit* `cell_choice`/`swap_samples` paths still hard-blocked (they had other cells available); **on 2026-08-07 that last block was removed too**, so no manual path blocks a clash any more.
  - **Exception (2026-07-29): a duplicate Pool ID's own earlier copy is exempt.** The carryover guard exists to stop a cell from being read twice for two *different* samples that happen to share a barcode — real cross-sample misattribution risk. It does NOT protect against anything when the "clashing" burn is from another copy of the *exact same* Pool ID (the "duplicate Pool ID" sample feature, `frontend/src/pages/SampleModal.tsx`'s "the same sample can be run across multiple cells"): reusing a cell with the identical physical material can't misattribute reads to a foreign sample, so there is no contamination risk either way (lab owner decision, reported after Auto Schedule/manual placement forced a multi-cell duplicate sample's later copies onto entirely fresh cells even while a tray it could have safely reused still showed spare capacity — the previous absolute rule blocked a duplicate's own barcode against itself exactly like a foreign one). `services/cell_service.py::barcode_owners()`/`foreign_barcode_clash()` now track *which Pool ID* burned each barcode on a cell, so only a burn from a genuinely different pool_id still blocks reuse; a self-burn is waived. Where the exemption still matters (the manual `_resolve_cell_choice`/`swap_samples` clash blocks it originally rode on were removed by 2026-08-07, so it no longer decides a manual *block*): the **clash FLAG** — `has_barcode_clash`/`is_duplicate_cell_reuse` (`cell_service.py`) — so an intentional same-Pool ID reuse reads as a benign duplicate (↻), not the "⚠ Clash" danger marking; and the **Auto Schedule / Recalculate engine** — `engine/packing.py`'s `pack_cells` via `PriorCellInput.barcode_owners`/`PackedCell.barcode_owners` (Auto Schedule/Recalculate — a fresh cell's *first* use must seed its own owner entry too, or its own second sample looks unowned and is wrongly treated as foreign). The waived case is surfaced, never silent: `StageOut.duplicate_cell_reuse` (`services/cell_service.py::is_duplicate_cell_reuse()`) marks the placement, shown as a ↻ on the grid's "N/M" duplicate badge and an info note in the slot-detail popover, and `has_barcode_clash()` (the QC-rezip "clash" flag) was narrowed the same way so it no longer misfires on an intentional duplicate reuse. Covered by `tests/unit/test_packing.py`'s duplicate-Pool ID cases and `tests/integration/test_cell_reuse_across_placements.py`/`test_placement_api.py`'s same-pool_id reuse tests. **Known gap, deliberately not touched:** the Cell QC "Stop cell" tray-reshuffle preview (`services/qc_service.py`'s independent `plan.clash` computation, distinct from `has_barcode_clash`) still applies the old absolute rule — a rare, separate workflow outside the scope of this fix; revisit if a QC reshuffle is ever reported forcing a duplicate off a cell it should be allowed to keep.
  - **Frontend gap fixed:** dropping a sample directly onto a specific waiting-cell ghost that turns out to share a burned barcode with it used to fail silently — `CellChoicePicker`'s auto-place logic (`cellChoiceGate.ts::shouldAutoPlace`) only ever checked whether the preselected cell was in the barcode-filtered `compatible` list, so an excluded (clashing) ghost just quietly fell back to opening a brand-new cell instead, with no indication to the user that their intended cell was rejected or why. Fixed by explicitly detecting a barcode clash on the preselected cell (`CellChoicePicker.tsx`'s `preselectedBarcodeClash`, compared against the *raw* open-cells list rather than the pre-filtered `compatible` one) and forcing the picker modal open with a prominent, specific warning (naming the clashing barcode and cell) instead of ever auto-resolving past it silently.

- **Later uses of a cell tend to yield less.** PacBio's own HG002 WGS data across 3 uses of the same cell (p.35) shows Use 3 consistently lower than Use 1/2 (e.g. 143.9 / 144.2 / 119.9 Gb; 147.0 / 148.6 / 124.7 Gb; 148.9 / 154.5 / 136.7 Gb), attributed to lower P1 loading efficiency on later uses — an expected pattern, not an anomaly (footnote, pp.35-36). This app doesn't model per-use yield/coverage at all today (the removed `engine/kpis.py` only ever did cost). If yield estimation is ever added, don't assume flat output across Uses 1-3 of a cell.

- **Sub-5kb amplicon libraries shouldn't go on multi-use cells.** PacBio: "For amplicon libraries <5 kb, using Revio SPRQ sequencing plate with multi-use Revio SMRT Cells may result in reduced P1/.HiFi yield performance for Use 2 and/or Use 3" (p.14) — the recommended path for those is single-use cells instead. **Now implemented (v0.47.0):** `Sample.insert_size_bp` is captured (importable via `import_fields.K_INSERT_SIZE`, editable on the backlog add/edit form) and `pack_cells` keeps any sample with `insert_size_bp <= insert_size_reuse_threshold` on a cell's **first use only** — never a 2nd/3rd (`engine/packing.py`'s `_cell_is_first_use` candidate-filter clause; a small-insert sample that can't get a fresh first use is reported unplaced rather than forced onto a reuse). Auto Schedule enforces this as a **hard rule**; **manual** drag/drop is allowed but surfaces a warning ("Samples <5kb have shown reduced performance of re-uses") plus a persistent `[<5kb]` card flag. The threshold is **admin-configurable**, not hardcoded: `settings_service.get_insert_size_reuse_threshold` (app_setting `scheduling.insert_size_reuse_threshold_bp`, default `engine.constants.DEFAULT_INSERT_SIZE_REUSE_THRESHOLD_BP = 5000`), read by `auto_fill`/`recalculate` and passed into `pack_cells` so the pure engine stays DB-free. Library-*type*-aware validation (amplicon vs WGS) is still not modelled — only insert size.

## Recalculate (2026-07-29)

"Recalculate" (a small ↻ button next to an instrument's name in the weekly grid) re-derives every one of that instrument's not-yet-loaded (`planned`) placements from scratch under the engine's *current* rules — for a schedule that was packed under an older or since-corrected rule (the duplicate-Pool ID barcode exemption above is the motivating case: a schedule built before that fix genuinely can't self-heal, since nothing re-visits an already-committed placement).

- `services/auto_fill_service.py::recalculate_instrument()`: finds every `planned` `Cycle` on the given instrument (any `load_date`, not just the visible week), bulk-unschedules their live (non-cancelled) placements back to the backlog via the same atomic `remove_samples()` "Clear schedule" already uses, then re-runs `auto_fill()` — full 3-use depth, every movie time, both trays, `"fewest"` objective — restricted via a new `sample_ids` filter to *exactly* the samples just freed. A `LOADED`/confirmed cycle is never touched (mirrors every other mutation in this module).
- **Deliberately narrow scope**: restricting to `sample_ids` (rather than letting `auto_fill()` draw from the whole current backlog, its normal behaviour) stops recalculating one instrument from reaching across and reassigning an unrelated sample that happens to be sitting in the backlog for a different reason. Without this, a lower-`pool_id`-sorting backlog sample could win a freed slot ahead of the very sample that used to occupy it.
- `POST /api/auto-fill/recalculate` (`api/auto_fill.py`), response shape identical to ordinary auto-fill (`AutoFillResponse`) since it's the same engine result, plus one recalculate-only field (`day_changed_sample_ids`, see the bug note below).
- Any sample that no longer fits once re-packed (e.g. a barcode conflict introduced by something scheduled elsewhere in the meantime) is left safely in the backlog and reported `unplaced`, never dropped.

**Bug found and fixed (reported 2026-07-29: Recalculate opened a second fresh tray for a same-day touchpoint instead of reusing the first tray's cells across two days, even with "fewest" and reuse-before-new both in play):** the day-slots offered back to `auto_fill()` were computed as *exactly* the instrument's existing planned `load_date`s (`load_dates = sorted({c.run_batch.load_date for c in planned_cycles})`) - never wider than whatever footprint the plan-being-replaced already occupied. `pack_cells()` caps every fresh cell's depth this batch at `min(max_uses, available_days)` (rule #5's "reuse before new" and the "fewest" objective's own most-used-first tie-break are both correctly implemented - see above - and were never the problem), and `available_days` is just the count of days `auto_fill()` is handed. So when every affected sample happened to already sit on a single day (e.g. 8 acquisitions of a duplicate Pool ID, all crammed onto one day's two carousel boxes), `available_days` came out to 1 and every fresh cell was capped to Use 1 - the packer had no choice but to open as many distinct physical trays as wells were needed that day, regardless of what "fewest" asked for. This directly undercut `recalculate_instrument`'s own docstring claim of "full 3-use depth," which was only ever true when the pre-existing footprint already spanned >= `CELL_MAX_USES` days. The existing regression test (`test_recalculate_consolidates_duplicate_copies_forced_onto_separate_trays`) didn't catch this because its fixture happens to seed two pre-existing days, which was already enough depth for that test's 2-copy case.

**Fixed** by extending the day-slots forward (weekdays only, from the latest existing load_date) until at least `CELL_MAX_USES` distinct days are on offer, never truncating an instrument that already spans more (`auto_fill_service.recalculate_instrument`). A candidate day auto_fill() genuinely can't use (already occupied, instrument-locked, or past a maintenance `down_from`) is skipped by its own existing pre-scan exactly as before - extending just gives the packer a fair chance to use a day it was never offered previously. Since this can now genuinely move a sample onto a day it wasn't on before - not just a different cell/tray, which is all the confirm dialog used to promise - `AutoFillResult.day_changed_sample_ids` (service layer) / `AutoFillResponse.day_changed_sample_ids` (API) reports exactly which samples that happened to, computed by diffing each affected sample's pre-recalculate acquire_date (captured before `remove_samples()` unschedules it) against its post-recalculate one (`AutoFillResult.sample_acquire_dates`, populated by every real `auto_fill()` call, recalculate or ordinary). Always empty for an ordinary Auto Schedule call, since a never-yet-placed backlog sample has no "before" day to diff against. Surfaced distinctly in the confirm-modal copy and the result Note (not folded into the plain "N placed" count) because a day change carries real lab-operational weight (collaborator commitments, staffing) that a cell/tray reassignment doesn't. Covered by `tests/integration/test_duplicate_barcode_reuse.py::test_recalculate_extends_into_a_new_day_when_the_existing_footprint_is_too_narrow_to_consolidate`.

Deliberately NOT applied to interactive Auto Schedule: its day range is the lab user's own explicit grid range-selection (`selectedCells`, `frontend/src/pages/SchedulePage/RunDesignFields.tsx`), never internally recomputed the way Recalculate's used to be - so silently widening it would create a run on a day the user never selected, which is a materially different (and more surprising) change than Recalculate extending its own already-invisible internal bookkeeping. If Auto Schedule is ever reported hitting the same starvation despite a wide user-selected range, look at *why* the selected days ended up narrower in effect (e.g. several silently skipped as already-occupied/locked - already partly surfaced via `skipped_cells` in the result Note) rather than reapplying this same forward-extension there.

**Bug found and fixed (reported 2026-07-29, same day: even with the day-window fix above, the consolidated schedule still didn't match what the lab actually does - the reused cell's 2nd use became a wholly separate run on the next day, rather than "Plate 2 of the same run"):** the lab owner's own words settle this: *"There is one run per day per instrument. Everything on that day is one run, whether it is one plate or two plates... the weekly schedule grid represents what the user does - the user loads two plates on one day, even if the instrument doesn't start sequencing it until the next day. It is the cell stubs that indicate what the machine does."* In other words: **the grid's day axis is when the operator racks a run in; a plate's own `acquire_date` (already a separate field on `Cycle`) is when the machine actually gets to it** - and those two are allowed to diverge within *one* run, exactly the way `placement_service.py`'s manual-placement-only intra-run reuse Plate 2 already models it (`_cell_used_in_run`/`_plate_target`: *"Plate 1 already holds it, this becomes the sequential Plate 2"* - `plate_index` there is a purely sequential/bookkeeping label, unrelated to which physical carousel box a well belongs to; `StageOut.slot_index`'s own docstring confirms *"a reuse Plate 2 sits in the SAME physical wells (A01-D01) as Plate 1"*). `auto_fill_service.auto_fill()`'s persist loop never used that mechanism - its `plate_index_of` was purely well-position-based (`2 if a.well in WELLS[CELLS_PER_TRAY:] else 1`), so a reused cell (always pinned to its own well, hence always the same box) could only ever compute `plate_index=1` again - meaning its reuse always spawned a brand-new, separate `RunBatch`, never "Plate 2 of the run its first use created." This was a deliberate design gap, not an oversight: the 2026-07-26 fix (below) had already removed an *equivalent* pairing shape from 1-plate-mode auto-fill because it caused two real bugs there (a "1 plate per run" choice silently showing 2 plates, and a reuse-chain race where Use 3 could start before Use 2 finished) - but that fix's own reasoning ("two-plate mode already worked this way") had assumed two-plate mode's per-day-run behavior was itself correct, when actually it had just never been asked to reuse a cell within a single recalculate/auto-fill batch before.

**Fixed** by giving `auto_fill()`'s persist loop the same model manual placement already uses, but ONLY when `cells_per_day == len(WELLS)` (2-plate mode - so 1-plate mode, and the "2 plates on Monday" bug it was fixed against, are completely unaffected; a 1-plate run never opens a Plate 2 at all). For each `PackedCell`, its uses are walked in chronological order (`uses_by_cell_ref`, already computed for the reuse-chain timing below): the **first** use behaves exactly as before (`plate_index` from well position - Plate 1's box, or a genuinely fresh, parallel second tray in Plate 2's box, same as ever). The **second** use bundles into the SAME `RunBatch` as the first, as its Plate 2, with `acquire_date` the later day it actually runs - *unless* that would collide with a genuinely different, fresh second tray already occupying that day's Plate 2 (tracked via `plate2_kind`, resolved in chronological order so a day's own native Plate 2 claim, if any, is always settled before any later reuse tries to bundle into it). A **third** use (or any cell whose own first use already fell in Plate 2's box, so it has no Plate 1 of its own to pair with) still starts its own separate run, exactly as before - a run holds at most 2 plates, so there's nowhere else for it to go. `get_or_create_run` needed no changes at all: passing it `plate_index=2, acquire_date > load_date` for an already-real Plate 1 makes it derive the bundled Plate 2's actual timing itself via the *existing* `reuse_plate_window` (Plate 1's real movie end; the on-board wash is the reuse cell's own prep now, not a load-time gap), the exact mechanism manual placement already relies on - so the reuse-chain-race bug from 2026-07-26 cannot recur here; that fix was about which `Cycle` a reuse's timing depended on, not about which `RunBatch` it belongs to. Covered by `tests/integration/test_auto_fill_api.py::test_recalculate_bundles_a_reused_cells_second_use_into_the_same_run_as_plate_2` (8 disjoint samples, forced onto one single day/two fresh trays before recalculate; after, consolidated onto 3 physical cells with Plate 1 = Use 1 and Plate 2 = Use 2 in ONE run, and a 3rd, genuinely separate run for the Use 3 overflow).

## Cadence / batching details consistent with current design

- **Run time is per-cell in this app, by deliberate product decision — a divergence from the vendor default.** PacBio run design applies one acquisition (movie) time to every well in a plate/run (12h/24h/30h). This app instead stores run time per well on `CellUse.run_time_hours`, so different wells of one run can carry different movie times; `Cycle.movie_hours` is kept as the run's *representative* (longest) value and drives `planned_end_at` + the instrument lock (`services/placement_service.py::recompute_cycle_timing`). This was chosen knowingly (see the git history / PR that added `CellUse.run_time_hours`) after the per-run constraint was surfaced — the lab owner wanted per-cell control. **Do not "fix" this back to a single per-run value without re-confirming with the product owner**; the mixing-rejection 409s that used to enforce one-time-per-run in `place_sample`/`move_sample`/`_move_sample_to_new_cell` were removed on purpose. Run time is set from the Run Design "Movie / run time" dial when a cell is placed or auto-scheduled, and is then editable per-cell from the slot-detail popover (`PATCH /api/cell-uses/{id}/run-time`). If real Revio firmware turns out to hard-require one movie time per plate, that's the constraint to re-litigate this against.
  - **Movie time also has a per-SAMPLE default now (v0.22.0).** `Sample.movie_time_hours` (nullable int, 12/24/30; null → 24h default, `engine.constants.DEFAULT_MOVIE_HOURS`) is importable (`import_fields.K_MOVIE_TIME`) and editable on the backlog add/edit form. A manual drag-drop omits `run_time_hours` from `PlaceSampleRequest`, and `place_sample` fills it from the dropped sample's `movie_time_hours` — so a sample runs for the movie time it was imported/edited with. The per-cell `run_time_hours` on `CellUse` (and its slot-popover editing) is unchanged; this only decides the *default* at placement. **Auto-fill now assigns each placed well its OWN sample's movie time** (`auto_fill_service.py`'s `_movie(a.sample)` → `run_time_hours`), and the Autoschedule panel's "Movie times" tick-boxes filter the backlog to the ticked lengths (`movie_set`, `auto_fill_service.py`); the old single "Movie / run time" dial is gone (`RunDesignFields`). **Per-sample movie length now also drives packing ORDER (v0.47.0 — the "prioritise movie length" the lab owner specced):** within one priority, position-constrained lengths (12h→cell 1, 30h→cell 4) are processed before flexible 24h so they claim their required well first — `engine/packing.py`'s `_movie_constraint_rank`, the new 2nd key in the `ordered = sorted(...)` tuple, right after `priority_rank`. This changes only *ordering*, not per-well *duration* (already per-sample). Net sample-processing order is now **Priority → movie-constrainedness → External ID → age → barcode heuristics**; the fragment-size first-use rule above is a separate hard *cell-choice* constraint layered on top, not part of this sort.
- Up to 8 sample wells per run across two sample plates, 4 cells per physical SMRT Cell tray (`WELLS` in `engine/constants.py`, 8 entries the code currently splits into tray-1/tray-2 halves — but a plate slot ≠ a cell-tray slot; see "Physical model" under "Plate vs cell") — matches the Revio's 4-stage-per-tray, 2-tray deck. `STAGES_PER_MACHINE = 4` only ever existed in the pre-redesign `revio-nx-planner.html` prototype (single tray, 4 wells); this app's port replaced it with the 8-well `WELLS` array once the two-tray loading redesign shipped — see "Instrument load-lock timing" below for how a run's lock duration depends on whether tray 2 is loaded too.
- **Loads are weekday-only; a reuse's own sequencing day may fall on a weekend (v0.55.0).** This app only lets a run be *loaded* on a weekday (PacBio's own examples use Mon/Wed/Fri runs — pp.19, 24-25, 32-33 — a lab-staffing choice, not an instrument limitation). But a reuse Plate 2 *sequences* when Plate 1's movie ends, which the machine runs unattended — so when this lab confirmed it runs weekends, the weekend-roll that used to push a reuse acquisition forward to the next weekday was removed. That roll turned a Friday-load reuse into a Monday acquisition, ~120h past the cell's Use-1 anchor and so outside the 108h window — which dropped the reuse candidate and opened a fresh tray instead of letting the tray reach Use 3. Now only `load_date` is weekday-gated (`place_sample`/`auto_fill`); a reuse's `acquire_date` may be a Saturday/Sunday (`placement_service._next_day` for the window-check floor, `reuse_plate_window` for the real acquire day/time). The grid still shows Mon-Fri columns only, so a weekend-acquiring Plate 2 renders inside its (weekday) load-day run card rather than getting its own continuation column.
  - **Auto Schedule reaches Use 3 from a single Friday load via a reuse-only *continuation slot* (v0.55.0).** Before this, a single offered load day capped a prior cell to one new use (`available_days = 1`), so a Friday-only Auto Schedule could only take a part-used tray to Use 2 and opened a fresh tray for the rest. Now, in 2-plate mode, `auto_fill_service` adds a `SlotInput(reuse_only=True)` for the **weekend** day right after each offered load slot (weekend-only by design: a weekday reuse day is simply offered as a load slot instead; a weekend never can be). `fill_slots` treats a `reuse_only` slot specially: it hosts **only** a cell's SECOND batch use (`idx == 1`, the bundleable Plate 2) — never a fresh first use (`idx == 0`) and never a 3rd+ use (`idx >= 2`, which needs its own separate weekday load) — and it neither is gated by nor advances the instrument load-lock. The persist loop's existing intra-run bundling then folds that continuation use into the origin run's Plate 2 (acquire = the weekend day, via `reuse_plate_window`), and a belt-and-suspenders guard there never creates a run whose `load_date` is a weekend. Net: a prior tray consumed once (Use 1 earlier in the week) reaches Use 2 (Fri, Plate 1) + Use 3 (Sat, Plate 2) from one Friday load. Covered by `tests/integration/test_auto_fill_api.py::test_single_friday_autofill_drives_a_prior_tray_to_use3_over_the_weekend`.
- **Reuse cell-prep carries a 45-min on-board wash, modeled as extra prep on the reuse cell (`REUSE_PREP_H = 0.75`).** PacBio's Revio v13.5 multi-use workflow adds ~45 min to cell prep time for Use 2 and Use 3 versus a single-use cell's one-time prep (p.33 footnote; qualitatively, reuse skips full manual immobilization — "automatic washing, no manual steps," cells "stay in instrument," p.19 — but still adds the wash step). This lives in the **one** timing model (`cell_timing.compute_timings` / `stageTimings.ts`): a first use preps `PREP_H` (4h); a reuse (Use 2/3) preps `PREP_H + REUSE_PREP_H` (4h 45m) — the cell is already in the instrument, so a reuse's turnaround before its next movie is the wash, not a fresh tray breakout, keyed off the cell's chronological use number (`cell_timing._is_reuse`, mirroring `run_serializer._use_number`). Because the wash is counted **once, in prep**, every timing surface reflects it together: the gantt, the instrument load-lock (`run_load_lock_end` — a run loading a reuse plate frees ~45 min later than the fresh-load ladder), the acquisition window, live instrument activity, and the reuse-readiness advisory (`cell_ready_at`/`reuse_not_ready_hours`). **`FIRST_PREP_H` was removed** — there was never a separate *stored* first-prep offset (prep lives in `cell_timing`). The reuse Plate 2's persisted load-time (`placement_service.reuse_plate_window`) is Plate 1's prep-aware movie **end**; the wash is no longer a load-time gap there, nor in `cell_service._ready_after` or `auto_fill_service`'s reuse chaining, so it is never double-counted. **The whole schedule now derives every timing from this one model** (unified, no fractured formulas): the persisted plate window (`planned_end_at`, derived on read in `run_serializer` via `cell_timing.coarse_movie_end` = load + prep + movie, + wash for a reuse plate), the reuse-day chain (`reuse_plate_window` / `auto_fill_service`, same `coarse_movie_end`), the reuse-readiness advisory (`cell_ready_at`), **and** the weekly grid's "reusable from" ghost (`waitingCells`, off the cell's prep-aware `CellOut.reuse_ready_at`) all use the same prep→movie definition. `planned_start_at` is the **load** (when the operator racks the plates); the movie starts `PREP_H` later (+wash for a reuse), so it no longer masquerades as the movie start and the old ~4h plate-box-vs-gantt split is gone. The one deliberate coarseness: `coarse_movie_end` omits the per-cell 2h breakout stagger (a within-tray gantt-only detail), so a per-plate day/window keys off the plate's representative movie, not its last-staggered cell — cells are still timed **individually** in the gantt/lock (`compute_timings`) and grouped **as a tray** (one load session) everywhere.
  - **A run's load time is user-chosen (8am-8pm) — the time the operator racks the plates.** By product decision there are no *pre-loaded* runs: the load time *is* Plate 1's `planned_start_at`, the moment the run goes on the instrument. The cells then prep (`PREP_H`, + the reuse wash for Use 2/3) before the movie starts — so load is the breakout/prep-start, **not** the movie start (this is why the old `FIRST_PREP_H` load-offset was never needed and has been removed; prep lives in `cell_timing`). The backend has always accepted `start_hour`/`start_minute` on `/api/cell-uses` and `/api/auto-fill` (default `DAY_START_HOUR`); the frontend now sends them: a manual first-drop onto an empty (instrument, day) opens a radial "load time" wheel (`frontend/src/components/scheduler/LoadTimePicker.tsx`, 08:00-20:00 hourly) before creating the run, and Auto Schedule uses the Run design panel's load-time control for every run it creates. Reuse Plate 2 timing chains off Plate 1's real (prep-aware) movie end (below), so choosing a later load time pushes the reuse's day/time out accordingly.
  - **A run's load time can also be amended *after* creation (v0.22.0), at Confirm-loaded.** `PATCH /api/cycles/{run_id}` accepts optional `start_hour`/`start_minute`; when present, `patch_run` calls `placement_service.update_run_load_time` *before* the status change, so a Confirm-loaded that also corrects the time locks the run with the corrected schedule. It moves Plate 1's `planned_start_at` to the chosen hour on the run's own `load_date`, `recompute_cycle_timing`s it, re-chains a reuse Plate 2 via `reuse_plate_window`, and moves a same-day parallel Plate 2 with it. **Deliberately NOT re-gated against a prior run's instrument lock** — unlike creating a run, this records/corrects reality for an existing one, so it never raises. The 108h clock still anchors at the real Confirm time (`update_run_status`'s running cascade sets `first_use_started_at = at`, not the planned start), so amending the load time only corrects the planned schedule/lock display, not the reuse-window deadline. Surfaced in the UI by a load-time control in the Confirm-loaded modal (`SchedulerDayCell`). Covered by `test_placement_api.py::test_patch_cycle_amends_load_time_at_confirm`.
  - **`reuse_plate_window` sets a reuse Plate 2's start to Plate 1's movie end (the on-board wash is the reuse cell's own prep now, not a load-time gap).** `placement_service.py::reuse_plate_window(plate1_start, plate1_movie, reuse_movie)` computes a reuse Plate 2's `acquire_date`/`planned_start_at`/`planned_end_at` as *Plate 1's real movie end* (no longer rolled forward over weekends as of v0.55.0 — a reuse may acquire on a Saturday/Sunday; see the "Loads are weekday-only; a reuse's own sequencing day may fall on a weekend" note above), and `get_or_create_run` calls it whenever it creates a reuse Plate 2 (any `plate_index == 2` whose `acquire_date > load_date`, i.e. Plate 1 already exists in the run). So the reuse day *reflects the movie length* rather than a flat "next weekday": for every allowed movie (12/24/30h) at the default noon start it still lands the next weekday (30h from Mon noon ends Tue 22:00 = load + 4h prep + 30h → reuse Tue), and only a late-in-the-day load or a very long movie pushes it further. It uses `cell_timing.coarse_movie_end` (= load + `PREP_H` + movie); the 45-min reuse wash is **not** added here — it's the reuse cell's own prep in `cell_timing`, counted once. This replaced two divergent, movie-length-blind computations that could disagree: the manual/derive path's flat `_plate_target` → `_next_weekday(load_date)`, and auto-fill persisting whatever slot day `fill_slots` floated the second use onto (`auto_fill_service.py`'s `acquire_date=a.run_date`) — the latter was the actual cause of a reported "Plate 2 shows Wed when it should be Tue" (the packer floated the reuse a day late when the immediate next weekday wasn't a free slot). Both paths now converge through `reuse_plate_window`; `_plate_target`'s returned date is only an advisory floor. **On the auto-fill/`fill_slots` interleave concern** (`fill_slots` plans reuse pairs before `auto_fill_service` groups them into reuse runs, so in principle it could schedule a fresh next-day run onto a day a reuse commits the instrument): this was checked exhaustively and found **not reachable** — in one-tray mode (`cells_per_day <= 4`, the only mode that produces an intra-run reuse Plate 2) the reuse cells sort ahead of fresh cells (`0 if prior else 1, -future_uses`) and fill the reuse day before any fresh cell can open, so no day ever mixes a reuse with a fresh first use; two-tray mode (`cells_per_day == 8`) makes each day its own run and never forms an intra-run reuse Plate 2. Verified across every objective, `max_uses`, and sample count 3-24, so no reuse-run-aware packing change is needed. Covered by `tests/unit/test_reuse_plate_window.py` and `tests/integration/test_auto_derive_cell.py::test_reuse_plate2_acquire_day_reflects_movie_length` / `test_auto_fill_api.py`'s reuse-day assertion.

## Instrument load-lock timing

Distilled from three additional PacBio slides (Revio scheduling/utilization examples, not in the numbered deck above) showing per-well acquisition timing and two "high-utilization schedule" Gantt examples. These informed `instrument_lock.py::cycle_lock_until()` - the function that decides when an instrument becomes available to start a brand-new (instrument, day) run.

- **Per-well timing inside one run:** cell prep is ~4h, offset by 2h between wells; PPA (post-primary analysis) starts 28h after loading and recurs every 28h for back-to-back acquisitions (4h prep + 24h sequencing); PPA itself runs ~14h for 4 SMRT cells (a single 2h offset + two 6h units). **The "two 6h units" is a capacity limit: an instrument runs at most 2 cells' PPA at once** — see the dedicated subsection "Per-cell breakout, PPA capacity, and instrument state" below, which is now the authoritative treatment. The estimated **stage-times gantt** (`frontend/src/utils/stageTimings.ts`, shown in the slot-detail popover and on the Instruments cards) models this per-well flow — prep → movie → PPA with the 2-lane PPA limit — as an illustration; the *backend* scheduler still does not consume per-well prep/PPA timing.
- **Example high-utilization cadences**, both averaging 24 SMRT cells/week: loading 8 cells per touch point (both trays at once) needs only 3 touch points/week (Mon/Wed/Fri, i.e. loads 48h apart); loading 4 cells per touch point (one tray) needs 6 touch points/week (Mon-Sat, loads 24h apart). The slides label the recurring per-touch-point window where the instrument accepts a new load as the "load window" - everything outside it is the instrument mid-run and unavailable to load.
- **The rule this app implements** (`instrument_lock.run_lock_until` → `cell_timing.run_load_lock_end`): the instrument frees to start a new run the instant the run's **last cell finishes prep** — `max(cell breakout + PREP_H)` from the per-cell timing model, **dynamic in the cell count**. One tray's cells finish prep at load+4/6/8/10h (4h prep, 2h-staggered); a second tray's cells can't prep until the first frees the 4 sequencing lanes (~28h), finishing at ~32-38h (capacity fact #3's ladder). Anchored on the run's **effective load** (`actual_start_at` once Confirm-loaded, else `planned_start_at`), so it reflects when the run actually started. **This replaced the old coarse `LOCK_BUFFER_HOURS` (6h, one tray) / last-movie-end + 6h (two trays) approximation** (v0.35.0), which mis-sized a small run (flat 6h regardless of 1–4 cells) and over-locked a two-tray run (movie-end vs the true last-prep-done), and keyed off planned start only. `LOCK_BUFFER_HOURS` now survives only as `engine/slot_scheduling.py`'s coarse *day-granular* auto-fill proxy (which lands on the same 1-day / 2-day gap).
- **UI note (as of the Autoschedule drawer):** the "Optimise for" control now surfaces exactly **two** choices to lab users — **"Fastest"** and **"Efficient"** — even though the engine and `AutoFillRequest.objective` still accept the wider legacy set (`"fewest" | "balance" | "fastest" | "utilisation"`). "Fastest" stores/sends `"utilisation"` (fill the tray so every sample starts sooner; each cell then has a running 108h expiry clock) and "Efficient" stores/sends `"fewest"` (reuse a cell to the Max-uses depth before opening the next, so fewer cells expire at once). The mapping lives entirely in the frontend (`frontend/src/pages/SchedulePage/RunDesignFields.tsx`'s `OBJECTIVE_OPTIONS`, typed by `Objective` in `frontend/src/types/schedule.ts`); the engine/tests below are unchanged. The `"balance"` and plain `"fastest"` engine modes are simply no longer offered in the UI.
- **Run design's "Cells per day" (4/8) and "Optimise for: Utilisation" controls directly implement the two example cadences above.** `AutoFillRequest.cells_per_day` (`schemas/run.py`) caps how many of a slot's 8 wells `fill_slots()` will offer per instrument-day (`WELLS[:cells_per_day]`, `engine/slot_scheduling.py`) - set to 4, auto-fill offers 4 display wells `A01–D01`; left at 8 (default), all 8. The wells are display/loading positions only — a prior cell whose home well is in the `A02–D02` box is still reused into these `A01–D01` wells by tray position (Stage 1 v0.40.1), so `cells_per_day` is a genuine per-day *sample cap*, not a "tray-1 only" restriction.) The `"utilisation"` objective (`engine/packing.py::pack_cells`) makes packing itself favor that same full-tray shape: unlike `"fewest"/"balance"/"fastest"` (which only ever tie-break between already-open candidates), it refuses to deepen reuse on any fresh cell until `cells_per_day` distinct fresh cells are open, so a touch point opens enough physically distinct cells to fill its wells before any of them starts a 2nd/3rd use - deepening only kicks in once that width is reached. Both are additive to the existing reuse-before-new-cell priority (rule #5 above), which is unaffected by either setting.
- This lock is explicitly a **planning tool**: it only gates *creating a brand-new* (instrument, day) run (`placement_service.get_or_create_run`) so a user isn't invited to schedule a run the instrument can't have started yet - see the "Gaps" note below on `planned` vs `running`. Adding more wells to an already-existing run is never blocked by it.
- ✅ **The gate is the dynamic prep-complete time everywhere (v0.35.0).** `run_lock_until` now returns `cell_timing.run_load_lock_end` (= `max(cell movie-start)`), so the serialized `RunOut.lock_until`, the grid's "locked until" continuation, and the new-run gate (`resolve_new_run_start` / `latest_lock_until`, used by both placement and auto-fill) all use the per-cell ladder off the real load anchor — matching the Revio-screen badge. The physically-correct free-to-load time (last cell's prep done: 1→4h … 4→10h one tray, 5→32h … 8→38h two trays) is what a lab user now sees *and* what the scheduler gates on.
- **UI label (v0.16.x):** the control that sets `AutoFillRequest.cells_per_day` is shown to lab users as **"Plates per run"** (`RunDesignFields.tsx`'s `PLATES_PER_RUN_OPTIONS`), not "Cells per day". **What it actually means (lab owner):** a **per-day sample cap** — **"1 plate"** = schedule at most **4 samples** that day, **"2 plates"** = at most **8**. It is *separate* from how many cell trays are on the instrument (those samples still run on cells drawn from whatever trays are loaded, reuse-before-new — including a tray in the other carousel bay, since v0.40.1/v0.40.2; see resolved "Gaps" #7). This label is also why the reuse-run shape below matters: a "1 plate per run" choice must actually produce one-plate runs.

### Per-cell breakout, PPA capacity, and instrument state (added 2026-07-28)

Distilled from a further PacBio slide — *"Scheduling PPA for evening with adaptive loading run design"* (instrument 84309, 2025/05/01–05/03) — which lays out one instrument's full two-tray schedule as a Gantt of five stages per cell: **Prep pending → Prep → Acquiring (movie) → PPA Pending → PPA**. The slide's own callouts are the authoritative timing facts:

- **Cell prep is 4h, offset by 2h** between the four cells of a tray (cell 1 preps first, cell 2 starts prep 2h later, etc.). A **reuse** cell (Use 2/3) adds the ~45-min on-board wash to its prep (4h 45m total) — it's already in the instrument, so its turnaround is the wash, not a fresh breakout; see the reuse-prep bullet under *Cadence / batching details* (`REUSE_PREP_H`). The fresh-load ladder below is unchanged; a run that loads a reuse plate simply frees ~45 min later.
- **PPA starts 28h after loading** (4h prep + 24h sequencing for the first cell) and **recurs every 28h** for back-to-back acquisitions.
- **PPA runs ~14h for 4 SMRT cells** = **a single 2h offset + two 6h "units"**. The two units are the key constraint: **an instrument can have at most 2 cells in PPA at any one time.**

**Three hard capacity facts, all inferrable from that Gantt** (an instrument is a small state machine over its resident cells):

1. **Sequencing capacity = 4.** One tray's four wells acquire in parallel (2h-staggered), so an instrument is sequencing at most 4 cells at once. A second tray's cells are *Prep pending* (queued) until the first tray's cells free the instrument — they do not sequence concurrently with the first four.
2. **PPA capacity = 2.** Only two cells can be in PPA simultaneously (the "two 6h units"). A cell whose movie ends while both PPA lanes are busy sits in **PPA Pending** until a lane frees. For a 2h-staggered tray of four 24h cells (movies ending at 28/30/32/34h from load), cells 1 & 2 enter PPA immediately (28h, 30h) and cells 3 & 4 wait ~2h each for a lane (34h, 36h), so all four finish PPA by ~42h — the slide's ~14h total PPA span (28→42).
3. **Awaiting-prep ⇒ locked; the instrument is free to load again the instant its *last cell finishes prep*.** While any resident cell is still *Prep pending* or *Prep*, the instrument is committed and cannot start a brand-new load; it frees the moment the last purple **Prep** bar ends. This is **dynamic in the cell count — not a flat buffer**:

   | cells loaded | free to load at (hrs from load) |
   |---|---|
   | 1 | 4 |
   | 2 | 6 |
   | 3 | 8 |
   | 4 | 10 |
   | 5 | 32 |
   | 6 | 34 |
   | 7 | 36 |
   | 8 | 38 |

   The ladder is `max(breakout + PREP_H)` over the run's cells: within one tray the four cells each prep 4h, 2h-staggered, so the 4th finishes at breakout 6h + 4h = **10h**; a second tray's cells are *Prep pending* until the first tray frees the 4 sequencing lanes (its movies end 28/30/32/34h from load), so cell 5 preps 28→**32h** … cell 8 34→**38h**. Equivalently it is `max(cell movie-start)` in `cell_timing` / `stageTimings`, since a cell's movie begins the instant its prep ends. (Figures from the *84309 2025/05/01–03* adaptive-loading slide — the purple bars.)

**Timing must be consistent across the app, anchored on two facts:**

- **Load time = the time entered at Confirm-loaded** — the moment the operator racks the plates (there is no separate pre-load). The cells then prep before the movie starts, so load is the breakout/prep-start, **not** the movie start; every downstream timing (movie, PPA, load-lock, reuse day, 108h anchor) derives from it via `cell_timing`.
- **Cell breakout is per-cell, not per-tray.** Cell *i* of a tray breaks out at **load + 2h·(i-1)** (cell 1 at load, cell 2 at +2h, cell 3 at +4h, cell 4 at +6h). Everything downstream of a cell hangs off *its own* breakout: its **108h reuse window** starts at its own breakout (so cell 4's deadline is load+6h+108h, ~6h later than cell 1's), its movie starts at breakout+4h prep, and its PPA at breakout+4h+movie (subject to the 2-lane PPA limit above). From load time alone the app can therefore say what any cell — and any instrument — is doing at any instant: awaiting prep / prepping / sequencing / awaiting-PPA / in-PPA / done.

**The single source of truth: `cell_timing.py` (added 2026-07-28).** The whole model above lives in one place, mirrored on both sides so the gantt and the backend agree cell-for-cell:

- **Backend** `backend/app/services/cell_timing.py` — `compute_timings()` is a pure lane scheduler (`SEQ_LANES = 4` sequencing lanes, `STAGGER_H = 2` adaptive-loading cadence, `PREP_H = 4`, `PPA_H = 6`, `PPA_LANES = 2`). A cell holds a sequencing lane from breakout to movie end, so a same-session second tray's cells wait for a lane and break out ~28h after load. `run_breakout_offsets()` adapts it to a run's cell_uses; `instrument_activity()` classifies each resident cell's phase (`phase_at`) at a moment.
- **Frontend** `frontend/src/utils/stageTimings.ts` — the identical algorithm (same constant names) drives the gantt.

**Bug found and fixed (reported 2026-07-26: Auto Schedule of a full week in "1 plate per run" mode showed "2 plates on Monday" and, after Clear, left a phantom instrument lock on Tue+Wed).** Two related bugs, both rooted in the old **one-tray reuse-run shape**:

1. **Auto-fill now creates one run per acquisition DAY in *both* plate modes** (`auto_fill_service.py`'s persist loop). The old one-tray shape (`cells_per_day <= 4`) *paired* a cell's Use 1 + Use 2 into a single **two-plate** run loaded on the Use-1 day (Plate 1 = Use 1, Plate 2 = the next-day reuse) — which the grid renders as two stacked plate boxes in the load-day cell, i.e. "2 plates on Monday", even though only **one physical tray is ever loaded per day**. That directly contradicted a "1 plate per run" choice. It now matches what two-tray mode always did: each day is its own run (`load_date == acquire_date`), a cell reused a later day forms a **separate one-plate run that day**, and the reuse is shown by the Use 1/2/3 grid colour rather than a second plate. `is_reuse` is therefore always `False` for auto-fill runs now (a run's plates all acquire on its own load day); the intra-run reuse **Plate 2** (`acquire_date > load_date`, timed by `get_or_create_run`/`reuse_plate_window`) is now reachable **only from manual placement** (`_plate_target`/`_cell_used_in_run`), never auto-fill. Reuse start-times are instead chained inside `auto_fill_service` (a cell's later use starts at the prior use's real movie end — the on-board wash is the reuse cell's own prep now, not a gap here — clamped to the packer's reserved day), which also fixed a latent overlap the old code had: it only chained a cell's *2nd* use (via the Plate 2 branch) and started a *3rd* use fresh at the load hour, so a 30h × 3-use cell scheduled Use 3 *before* Use 2 finished. 2. **Clear (and multi-select Remove) is now one atomic transaction** (`POST /api/cell-uses/bulk-remove` → `placement_service.remove_samples`), not one concurrent `DELETE` per stage. The per-stage path fired `Promise.allSettled` over N requests; each `_cleanup_emptied_plate` deletes a plate/run only once its stage-count hits zero, guarded by a `FOR UPDATE` that is **a no-op on SQLite** (dev). Concurrent removals could therefore race the count check (or partially fail on `database is locked`) and strand an **orphaned empty cycle** — for the old paired shape, the Tuesday-acquiring reuse Plate 2 — which then kept projecting a lock/continuation onto Tue (via `acquire_date`) and Wed (via `lock_until`, a 24h movie + buffer), i.e. a "lock" on days with nothing scheduled. Running every removal in one transaction makes `_cleanup_emptied_plate` always see a consistent count, so an emptied plate/run is always fully deleted. **Defence-in-depth:** an empty cycle (no `cell_uses`) is now *never* treated as loaded — `run_serializer.run_out` drops it from a run's plates and reports the run unlocked, and `instrument_lock.run_lock_until`/`_candidate_runs` ignore it — so any orphan already in a DB (or arising some other way) can't project a stale lock. Covered by `test_auto_fill_api.py::test_clear_via_bulk_remove_leaves_no_orphaned_lock` and `test_an_orphaned_empty_cycle_is_never_a_plate_or_a_lock`.

## Instrument maintenance-down (operational, not vendor-derived)

Separate from the load-lock above, an instrument can be flagged **down for maintenance** from a date (`Instrument.down_from`, set via the Instruments tab / `POST /api/instruments/{id}/maintenance`). This is an **operational lab constraint, not a PacBio-documented instrument behaviour** - it models "this Revio is physically out of service" (laser swap, service visit, etc.), not anything in the vendor deck.

- **Where it's enforced:** the same single chokepoint as the load-lock - `placement_service.get_or_create_run` refuses to create a brand-new run when `down_from is not None and load_date >= down_from` (raising `PlacementError(409)`), and `auto_fill_service` skips such a slot in its pre-scan (same "skip, don't hard-fail the batch" UX as an already-locked day). Like the load-lock, it gates only *new-run creation*; a run already scheduled before the down date, and adding wells to an existing run, are untouched.
- **Open-ended:** `down_from` has no paired "until" date - the instrument stays down until explicitly brought back online (`POST /api/instruments/{id}/online` clears it). Distinct from `Instrument.active` (the permanent retire/hidden-from-schedule flag): a down instrument still renders in the grid, greyed from `down_from` onward.
- **Frontend mirror:** the Schedule grid greys and disables day-columns on/after `down_from` (`SchedulerGridRow`/`SchedulerDayCell`'s `down`), so the client can't offer a selection the backend would reject - but the backend re-validates regardless, never trusting the client.

2. The 108h check applies uniformly regardless of which use is next (2nd or 3rd) — this matches PacBio's stated single-deadline behavior (see above), but if the instrument's actual firmware ever turns out to differentiate by use-index, or the SMRT Link "start within" countdown (p.29) implies something more granular, revisit `recompute_status()`.
3. **~~No insert-size / library-type-aware validation exists~~ — RESOLVED (v0.47.0, insert size).** `Sample.insert_size_bp` is now captured, and `pack_cells` keeps a small-insert sample (`insert_size_bp <= insert_size_reuse_threshold`, admin-configurable, default 5000) on a cell's first use only, with a manual-placement warning + `[<5kb]` flag on a 2nd/3rd use (see "Sub-5kb amplicon libraries" under "Rules worth mirroring…" above). 5. The rejected alternative (b) — a strict `CellUse.well == home_well` model where a cell only ever renders in its own tray-position slot — was simpler to reason about but would have left a spent cell A's slot A01 empty and pushed new loads to cell B's own slot B01, contradicting the "A01 could take cell B Use 1" expectation.
7. **~~The code ties plate position to carousel box / cell tray (over-constrained)~~ — RESOLVED (Stage 1 v0.40.1, Stage 2 v0.40.2, 2026-07-30).** The real instrument keeps cell trays and sample plates in independent positions, and a plate can be backed by cells from *either* tray (see "Physical model" at the top of "Plate vs cell"). The over-constraint was: `derive_best_cell`'s `_cell_box != box` filter (`placement_service.py`), `fill_slots`' `WELLS[:cells_per_day]` well-pinning (`engine/slot_scheduling.py`), and `open_new_tray`'s drop-well-derived box collision (`cell_service.py`) all treated "Plate 1 = tray-1 wells `A01–D01` / Plate 2 = tray-2 wells `A02–D02`", so reuse — and fresh-tray allocation — were locked to a box. Symptom: a **1-plate Autoschedule placed 0 samples** when the reusable cells sat in the `A02–D02` box (they were refused, `pack_cells` packed the backlog onto them reuse-before-new, `fill_slots` stranded every one), and a fresh tray couldn't open when the drop well's bay was occupied even if the other bay was free (`open_new_tray` `ValueError`, swallowed → dropped/409). **Fixed:** (Stage 1) `fill_slots` reuses a prior cell into any free same-*position* offered well, with a `box_tray` tray-cohesion guard; (Stage 2a) `derive_best_cell`'s box filter deleted (`_plate_box`/`_cell_box` removed) so manual place/move reuse across boxes; (Stage 2c) `open_new_tray` selects a free cell-tray **bay** (drop well's own if free, else the other; raises only if both occupied) and the auto-fill persist block resolves the fresh cell by `within_tray_pos`. A cell reused/loaded cross-box keeps its home-well identity while `CellUse.well` is the drop well (the loading-well≠home-well split, rendered via `run_serializer._slot_index`). One-tray-per-plate cohesion is preserved throughout (`_established_tray_id` / `box_tray`, both `tray_id`-based, never box-based).
8. **QC reshuffle still applies the absolute (pre-2026-07-29) barcode rule.** The duplicate-Pool ID reuse exemption (see "Rules worth mirroring… Barcode carryover" above) was applied to both scheduling paths (manual placement, Auto Schedule/Recalculate) but deliberately NOT to the Cell QC "Stop cell" tray-reshuffle preview/commit (`services/qc_service.py`'s own independent clash computation) — a separate, much rarer workflow outside that fix's scope. If a QC reshuffle is ever reported forcing a duplicate sample off a cell it should be allowed to keep (another copy of its own Pool ID), extend `qc_service.py`'s reassignment planner to use `cell_service.foreign_barcode_clash`/`barcode_owners` the same way.
